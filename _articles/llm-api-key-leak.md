2026年8月29日，Anthropic开始向一批Claude用户发送紧急通知：你的账号已被强制下线，绑定的信用卡也已被移除。这不是因为Anthropic自己被攻破，而是因为用户自己的电脑上潜伏着信息窃取木马。这些木马偷走了浏览器里已完成认证的Claude会话凭证，攻击者直接拿去消耗付费额度——密码和MFA，一步都没碰。

事实上，从8月起就陆续有用户在社交平台反映账号疑似被盗，额度被莫名其妙地消耗。一位用户称，自己在毫不知情的情况下被额外扣除了约800欧元；还有Reddit用户描述了自己的经历：先是社交媒体账号被盗，随后发现系统已被感染，而木马的源头，正是一个破解版游戏下载。

> Anthropic在通知中写得很直接：
"If your usage limits looked like they refilled and then drained while you weren't using Claude, this was likely the cause."
翻译过来就是：如果你明明没用Claude，额度却莫名其妙地满了又空了，大概率已经中招。

可以看到，针对公网大模型服务的凭证窃取与泄露问题，已经严峻到不容忽视。因此，我们写下这篇研究文档，层层拆解这起事件的来龙去脉，欢迎少侠们耐心食用。

# 公网大模型密钥泄露：攻击面、提取手法与防御

2026年5月8日，CISA把LiteLLM的CVE-2026-42208列入已知利用漏洞目录（KEV）。KEV 的收录门槛是在野利用的确凿证据，收录即要求美国全体联邦机构限期修复。
![描述](/assets/images/llm-api-key-leak/screenshot-20260831-194752.png)

LiteLLM作为一个开源AI网关，它的SQL注入漏洞，竟然被提到了国家级应急响应的优先级，这足以说明AI安全已经举足轻重。
> LiteLLM 是一个开源的 AI 网关与 Python 库，旨在通过统一的 OpenAI API 格式来简化和管理对全球 100 多种大语言模型（LLM）的调用。`

Cloud Security Alliance在事后分析还原了攻击者针对这个漏洞的动作，在漏洞公告进入公开数据库不到36小时，已经发现在野利用，攻击者在攻击过程中用17个UNION攻击载荷，意图枚举数据库结构后，主要观察三张表，分别是`LiteLLM_VerificationToken`、`litellm_credentials`、`litellm_config`。这三张表正是LiteLLM运行后，存放所有上游LLM供应商Key的地方。
因为攻击者在整个利用过程没碰别的数据，目标从第一步起就是凭据。
因此，CSA对相关事件的定性是“存放组织级供应商凭据的LiteLLM实例被攻破，其危害等同于整个云账户失陷。”
![描述](/assets/images/llm-api-key-leak/粘贴图-212847.png)

那么，这起漏洞利用事件出现之前，有无先例呢？事实上，这不仅不是孤立的漏洞事件，在当时就已经形成了相对比较成熟的产业链。

在Sysdig2024年命名LLMjacking时，估计的受害账户的账单是每天损失46000 美元（AWS Bedrock 满配额消耗），而到了CSA 2026年的追踪中，已经把商用大模型场景的用户损失推算到每天 100,000 美元以上。Pillar Security归因的Operation Bizarre Bazaar事件中，发现40天的记录里面存在35000多个攻击会话，变现方式从挖矿、暗网转售API访问到窃取提示词和对话历史。偷来的访问经反向代理包装成"低价 API"转售，买家永远碰不到凭据，追责在中间商断链。

可以发现，攻击者的纪律性已是商业水准，具体表现是，动手前先探测目标的调用日志是否开启，确认无审计再开始消费。

泄露的入口规模同样量级惊人。GitGuardian [《2026 秘密蔓延状态报告》](https://blog.gitguardian.com/the-state-of-secrets-sprawl-2026/)（第五版，2026 年 3 月发布）统计：2025年公开GitHub新泄露敏感配置2865万个，同比增长34%，是有记录以来最大的单年增幅；其中AI服务类凭据1275105个，同比暴涨81%，仅DeepSeek API Key一项就流出11.3万个，全部类别里增长最快的10种有8种与AI服务相关。

国内有独立的全国级数据，中国电信云堤（有幸曾经有合作过），看他们广目平台2026年8月的测绘显示，恶意事件占比最高的不是暴露量最大的Ollama（占全网暴露 87.17%，恶意事件占比反而不高），而是只占暴露面11.46%的LiteLLM，它的恶意事件占比47.03%，接近一半。虽然攻击者一开始扫的肯定是整个暴露面，但下手的时候肯定集火钱最集中的网关。

利用同一份测绘对象，连续两周追踪1000多个暴露目标，发现两周后约40%关停，补上登录认证的只有约 1%，超过一半原样开放。

在近期Wiz蜜罐观测中，发现Qilin 勒索软件组织与LiteLLM漏洞链的活跃利用存在关联，也就是说大模型key泄漏，危害不止是刷账单，是加密勒索。
![描述](/assets/images/llm-api-key-leak/粘贴图-004210.png)

另外还有两份全球报告也要关注：

Verizon [《2026 数据泄露调查报告》](https://www.verizon.com/business/resources/reports/dbir/)（DBIR）中，描述了企业设备上定期使用AI的员工比例一年内从15%涨到45%，其中67%走的是个人账号，这种情况下，企业管控是很难开展的；Shadow AI成为DLP数据集里第三常见的非恶意内部行为，同比增长4倍；员工提交给外部大模型最多的数据类型是源代码。

Google Cloud [《威胁视野 H1 2026》](https://services.google.com/fh/files/misc/cloud_threat_horizons_report_h12026.pdf)（基于 Mandiant 应急响应数据）：云和 SaaS 环境的入侵事件中 83% 由身份问题开启，21% 直接使用被盗凭据；漏洞披露到在野大规模利用的窗口从以周计压缩到以天计，React2Shell（CVE-2025-55182）公开后约 48 小时就出现了部署 XMRig 矿马的实例。

常言道，事件代表严重性，规模解释必然性。

结果显示，Dify全球对公网暴露的资产有58,000+ 个（中国占52%，其中阿里云占43%）、Open WebUI有104,000+ 个（中国29%、美国20%）、RAGFlow4,800+个（中国3,200+，阿里云57%）、AnythingLLM 6,600+ 个（前五市场占78%，AWS60%）、Langflow约2,500 个、NextChat7,600+个。

通过绿盟的测绘报告，我们可以从攻击者视角得出结论，那就是这批暴露实例的共性问题不是某个漏洞，而是API未授权访问，未鉴权接口直接返回向量库配置、模型版本、Key 调用状态。这与本文后面第四章Flowise实测、第六章四台国内系统的结论一致：暴露面的大头是鉴权缺失，并不是Nday利用。

因此，我们将在本次课题研究中，思考一个问题：**公网大模型的 Key，是怎么被拿的。** 对暴露公网的持 Key 系统，面板、网关、Agent 平台、MCP 服务器、云 IDE进行脆弱性利用；以及通过钓鱼、供应链投毒、抢注AI幻觉出的包名等手法进行分析。

## 一、威胁模型：为什么API Key是新的高价值目标
{: #ch01}

### 1.1 Key不适用密码的防护思路
{: #ch01-1}

传统的针对密码的安全模型，都是建立在"使用者是人"的假设上。比如人会忘记，所以有重置流程；人会泄露，所以有定期轮换；人有行为特征，所以有异常登录检测。而API Key的安全模型是没有这些假设的，Key 是给程序用的，配置一次长期有效、以明文形式存在于配置文件和环境变量里、调用时无任何行为特征可供画像。

两者的差异在失窃后最为明显。密码失窃，攻击者还要过第二因子、过设备指纹、过异地登录风控。Key 失窃，攻击者直接持有一个完整的合法身份。所有大模型供应商的SDK里，Key的语义就是记账凭证，请求头带上Key，账单记在 Key 所属账户上。比如，如果攻击者偷到一个OpenAI的`sk-proj-`前缀的Key，攻击者不需要任何后续步骤，直接调用，之后的成本损失全部由被偷方承担。

### 1.2 失效机制：99.5%的泄露Key会自动触发
{: #ch01-2}

Intezer和Unit 42用YARA规则在VirusTotal语料里，发现647个泄露的唯一大模型 Key（Android APK 样本占 62%，其中最多的是 Gemini Key），验证方法是发轻量GET请求，不发提示词，却发现**99.5%的泄漏的Key已失效**。

为什么会这样呢，因为大模型供应商持续扫描公开语料，发现自己格式的Key就自动撤销，从而降低用户的损失，而且这个机制对攻击者的筛选意义，是大于对防御者的安慰意义的。但是这个机制毕竟还是基于公开语料被扫描到的场景，如果流入私密渠道没被扫到的（持续存活），那么将很难触发这个机制，而攻击者攻击的主要对象正是后者。我在第5.3节实测的时候发现有6条key疑似真实Key，来自凭据库匿名可读的实例，恰恰是"没有流入公开语料"的那个类别。

因此，除了供应商的自动撤销之外，企业侧的轮换治理动作基本不会出现。GitGuardian 在[《2026 秘密蔓延状态报告》](https://blog.gitguardian.com/the-state-of-secrets-sprawl-2026/)里追踪2022年泄露且确认有效的秘密，结果显示2026年1月复测时仍有 64% 未被撤销；Mandiant 在 2025 年末的真实入侵响应里，确认攻击者使用的正是2022年某密码管理器事件中泄露的AWS Key。因此，企业侧究竟有多少账号、key资产被恶意利用，难以想象。

### 1.3 判断：藏得深不属于防御
{: #ch01-3}

攻击者获取Key路径的方式通常是是读源码，官方SDK、开源网关、开源平台的代码本来就是公开的，其中关于Key的存储位置、加载方式、内存形态都是白盒。
在这种情况下，防御者把Key藏进 `.env`、藏进环境变量、藏进Vault，防的是"顺手翻文件的低能力攻击者"，对读过源码的攻击者无效，因为他比产品或者运维本人更清楚这个框架的Key在哪。
比如，攻击者知道LiteLLM的master key不存储在文件系统中，于是从进程内存读；知道Flowise的认证中间件是条件启用的，于是直奔无认证的2.x实例；知道Ollama自己不存 Key，于是穿过它去读宿主机文件系统。

## 二、攻击者的资源获取模型
{: #ch02}

>  Intezer是一款由人工智慧驅動的自主安全運營中心（Autonomous AI SOC）平台，旨在幫助企業自動化處理、調查和回應各類資安警報。

![描述](/assets/images/llm-api-key-leak/粘贴图-125707.png)

Intezer 把攻击者获取大模型推理能力的途径整理成五条，这张表解释了"为什么偷你的最划算"：

| # | 途径 | 前沿算力 | 与本文目标的关系 |
|---|---|---|---|
| 1 | 地下攻击性模型（WormGPT、GhostGPT、KawaiiGPT、Xanthorox） | 弱，无审查但能力有限 | 替代品 |
| 2 | 加密支付的第三方 LLM 服务（身份在中间商断链） | 强，但贵且账户会被封 | 替代品 |
| 3 | 免费版与无密钥公共 API | 中，量级够用 | 替代品 |
| 4 | 暴露或被盗的 Key | 强，但 99.5% 已失效 | **正中靶心** |
| 5 | 暴露的自托管服务器 | 强，无审查且无限配额 | **正中靶心** |


途径3，可以先提一嘴，比如Groq、Cerebras、HuggingFace、OpenRouter这些，都提供免费的部分服务，一次性邮箱注册即可获得配额，通过公共清单（cheahjs、mnfst）能直接测出免费池的规模。基于所给的免费额度，是可以满足侦察、轻量生成、批量钓鱼邮件这类任务的。

攻击者实际上真正必须偷算力的场景，主要聚焦在大规模数据抽取、自动化渗透、长时间运行的Agent，任务重、运行时间长，所以攻击面数据里真正被反复光顾的，是能扛重负载的自托管实例。

途径4和5之间有一个关键的资源属性差异，Intezer的结论是"暴露服务器是最持久的途径"，因为**Key是主动资源，可以被轮换、会被供应商自动撤销；算力是被动资源，只要机器开着就在。** 

当成熟的攻击者面对一台暴露的机器，先评估的不是"里面有几把 Key"，是"这台机器能持续用多久"。这个差异直接决定防御的优先级，只管Key不算完整防御，跑Key的机器本身暴露与否是同一个问题。换言之，如果key能确保前端不泄漏，但是相关服务被攻击者控制使用，损失是非常直接的。

## 三、目标系统分类分级
{: #ch03}

从攻击者视角，可以按照这两个维度给公网的系统分类，**Key 密度**（一个实例里存多少Key）和**认证强度**（默认配置下Key抗攻击能力）。

**第一梯队：网关层。主要是** New API、One API、LiteLLM，它们里面的Key密度目前生态内最高，一个进程集中存着全公司或全团队的上游Key。一般使用这类系统，是为了做降本和管理，多个业务共享少数几个上游账号，通过网关统一计费、限流、路由。但是集中存储的同时，单点风险也集中了。

LiteLLM的 proxy模式是典型攻击对象，在它的SDK模式下，Key分散在每个调用方，然后proxy模式下所有Key汇进一个进程。在企业内部，通常会使用Docker将LiteLLM Proxy部署为独立服务，作为内部的 AI 中台：
```
# docker-compose.yml 示例
version: "3.9"
services:
  litellm:
    image: ghcr.io/berriai/litellm:main-latest
    ports:
      - "4000:4000"
    environment:
      - OPENAI_API_KEY=sk-...
      - ANTHROPIC_API_KEY=sk-...
    volumes:
      - ./config.yaml:/app/config.yaml

```
通过配置 config.yaml，运维人员可以设定负载均衡策略（Load Balancing），比如当 OpenAI 响应超时时，自动回退（Fallback）到 Azure OpenAI。


**第二梯队：Agent 应用平台层。主要是** Flowise、Langflow、Dify、n8n、FastGPT、RAGFlow等应用，它们一般呈现为低代码或工作流形态，替用户保存各模型供应商的Key，用户拉个流程就能调用。这一层的共同特征是默认部署极简（docker 一行命令）和默认无认证或弱认证，服务的是快速原型验证场景，但是过轻的部署，总是被AI时代的使用者遗忘，好像信息过载导致用户自己也承受不了自己安装过什么的记忆，于是大量实例停留在"试了一下就扔在公网"的状态。

**第三梯队：开发环境层。主要分为**code-server、Jupyter、暴露的终端和IDE。这一层不持有"平台的Key"，持有的是"人的 Key"，比如Claude Code、Codex CLI、Continue插件的凭据，路径固定且公开。

三梯队的攻击逻辑不同：打网关是为了一次拿全部Key，打平台是为了拿用户存的Key加RCE，打开发环境是为了拿个人身份的Key。

下面四章按动手深度依次展开。

## 四、Ollama：自己不存Key，却是偷Key的最佳入口
{: #ch04}

### 4.1 架构决定了它没有认证
{: #ch04-1}

Ollama的API面（`/api/generate`、`/api/chat`、`/api/tags`、`/api/pull`、`/api/delete`）设计上不存在认证，简单来说，就是Ollama没有相关的api Key来校验中间件，没有用户体系，`OLLAMA_*` 环境变量族里没有一个存密钥。这是产品定位的原因，Ollama面向的是本机开发者场景，默认绑定 127.0.0.1，因此产品方认为认证在这个场景里是没有意义。
![描述](/assets/images/llm-api-key-leak/粘贴图-170227.png)

但是如果在部署变更时，需要实现局域网或公网访问，运维人员通常会设置 `OLLAMA_HOST=0.0.0.0`，这个环境变量一改，一个没有任何认证机制的API就直接暴露了，等于把GPU算力白白贡献给非内部人员。

Sysdig在2026年6月发布的报告中，描述了这条攻击路径当前的实现现状。偷来的Ollama算力不再被转卖或用于聊天，而是被接成**多阶段自动化渗透工具的决策工具**，执行链是指纹识别、CVE 匹配、PoC 生成、盲SQLi构造、凭据提取、循环到RCE。在Sysdig报告中，这个攻击者的工具主要访问7个商用模型（gpt-4o-mini、claude-3-5-sonnet、gemini-2.0-flash-exp 等），然后全部重指向免费的Ollama后端。被捕获时它正处于8小时开发会话中，目标是RFC 1918内网段和HackTheBox靶场。

但算力白嫖只是Ollama的第一层价值，因为攻击者真正想要的Key本身就不在Ollama里，随即攻击者把目光瞄准了宿主机。

### 4.2 Probllama：从无认证端点到 root 级任意文件读
{: #ch04-2}

CVE-2024-37032（Probllama，Wiz 2024 年 5 月披露，0.1.34 修复）是整条链的桥。
![描述](/assets/images/llm-api-key-leak/粘贴图-171015.png)

`/api/blobs/<digest>` 端点把 digest 参数直接拼进文件路径：

```
GET /api/blobs/sha256:../../etc/passwd
```

路径参数未做规范化校验，URL 编码的 `%2e%2e%2f` 可以跳出模型存储目录读取任意文件。Ollama 的 systemd 服务默认以 root 运行，所以这个文件读是 root 级的，`/etc/shadow`、任意用户的 home 目录、其他服务的配置全部可读。

读任意文件的能力要转化成凭据，靠的是对宿主机上"还跑着什么"的理解。国内最常见的部署形态是一台机器 docker-compose 同时起 Ollama 和 New API、LiteLLM 或 Dify，无认证的算力入口和 Key 集散地被焊在同一个文件系统上。审计脚本按这个模型做凭据狩猎，先读 `/etc/passwd` 枚举全部登录用户的 home 目录，再逐个扫描：

```
~/.bash_history  ~/.zsh_history        # export OPENAI_API_KEY=sk-... 的明文记录
.env  docker-compose.yml               # 同机混部网关的上游 Key
~/.continue/config.json                # Continue 插件
~/.claude/settings.json                # Claude Code 的 ANTHROPIC_API_KEY
~/.codex/auth.json  ~/.cursor/         # Codex CLI、Cursor
~/.config/JetBrains/*/options/         # JetBrains 系 AI 插件
~/.config/Code/User/settings.json      # VS Code（Copilot 等）
/proc/self/environ  /proc/1/environ    # 进程环境变量
/var/run/secrets/kubernetes.io/...     # K8s ServiceAccount token
```

需要注意，为什么要读上面这些文件，比如`.bash_history` 是命中率最高的路径，因为开发者习惯在 shell 里 export Key 再启动服务，这条历史文件就成了明文 Key 的持久化备份，比任何配置文件都稳定，因为它不会随服务重装被清理；而`/proc/1/environ` 是容器场景的特例，容器里 PID 1 就是主进程，它的环境变量是 docker-compose 里声明的全部上游 Key，读一个文件等于拿到整个混部栈的凭据清单。

### 4.3 审计数据思路
{: #ch04-3}

这条攻击链的审计实现（`ai_ollama_keyaudit.py`，纯标准库）分五步：

```
[1] 版本探测        0.1.34 分界，标注 Probllama 影响范围
[2] 暴露面          无认证模型清单、工具调用能力启发式、CORS 通配符检测
[3] 穿越探测        CVE-2024-37032 五种编码变体，用 /etc/hostname 无害确认
[4] 凭据狩猎        /etc/passwd 枚举 home，逐用户扫描上表全部路径（只读）
[5] Key 提取        11 类正则 + 环境变量赋值兜底，每条结果定位到文件与上下文行
```

说一下步骤细节：

穿越探针选 `/etc/hostname` 而不是敏感文件，判定逻辑是"能否读到一个已知存在且无敏感性的文件"，确认漏洞存在即停。

五种编码变体（literal、encoded、sha256-prefix、mixed、double-encoded）是因为不同实例前面的反向代理对路径的处理行为不一致，有的会解码后再转发，有的原样透传，否则单一的写法会漏报。

Key提取不用单一正则覆盖，因为OpenAI、Anthropic、DeepSeek、Moonshot、AWS、GitHub、Google、Slack、智谱、私钥、JWT 这 11 类有确定形态，而且企业内部自建token没有统一格式，所以攻击者是靠 `ENV:XXX_TOKEN` 标签来进行识别，也就是说识别的是"环境变量赋值"这个行为特征而非 Key 形态。

### 4.4 本章结论
{: #ch04-4}

可以发现，Ollama的风险不只是自身算力被利用，还有对于宿主机文件系统的威胁，因此给Ollama加认证解决的是入口问题，宿主机的治理，事实上是另一个独立的且更严重的问题，涉及history、本级文件的保存等问题。

## 五、Flowise：认证模型的条件缺陷
{: #ch05}

### 5.1 认证中间件是条件启用的
{: #ch05-1}

Flowise 是低代码Agent平台，docker一行命令就可以启动，替用户保存各模型供应商的Key。

![描述](/assets/images/llm-api-key-leak/粘贴图-173008.png)


它不像Ollama，是有认证功能的。但它的认证模型有个容易被忽略的细节，**2.x 版本线的认证中间件只在 `FLOWISE_USERNAME` 和 `FLOWISE_PASSWORD` 两个环境变量同时设置时才挂载。**

那么，默认 `docker run flowiseai/flowise` 是不携带任何变量的，中间件不存在，全部API可以匿名访问，官方当然不会认为这是漏洞，因为官方文档假设用户会自己加认证，且假设用户在本机部署。

所以造成了在实际公网的暴露面测绘过程中，我们发现大量实例就停在这个默认状态，并对公网进行暴露。

![描述](/assets/images/llm-api-key-leak/粘贴图-173728.png)


### 5.2 拿Key的四条路径
{: #ch05-2}

**路径一：CVE-2025-59528，未授权 RCE，CVSS 10.0。** CustomMCP 节点把用户传入的字符串直接交给 `Function()` 构造器执行。影响 3.0.5 及以下。CSA 的研究笔记确认该漏洞处于活跃利用状态，攻击目标就是 LLM provider Key。RCE 之后整个文件系统和数据库都可读。

**路径二：GHSA-6pcv-j4jx-m4vx，loginmethod 泄露 OAuth Client Secret。** `GET /api/v1/loginmethod` 是登录页用来判断启用哪种登录方式的端点，未认证可访问，响应体里带 Google OAuth 配置，包括 clientSecret。一个匿名 GET 拿到一个可用的 OAuth 客户端凭据。

**路径三：chatflow 内联的 Key。** 用户在画布上配置节点时把 Key 直接填进组件参数，Key 就保存在 flow 配置 JSON 里。无认证实例的 `/api/v1/chatflows` 匿名可读，内联 Key 直接暴露。这是用户行为造成的泄露，不依赖任何 CVE。

**路径四：凭据库。** 2.x 无认证实例的凭据管理 API 全部匿名可访问。响应里有分层：标准组件的 password 类型字段被服务端脱敏，返回 `_FLOWISE_BLANK_` 占位值；自定义组件和非 password 类型字段不做处理，直接返回明文。

### 5.3 选取部分公网实例的形态判定
{: #ch05-3}

通过公开的脚本对FOFA宽指纹筛出的 422 台Flowise进行分析，对第三方实例只做漏洞识别，根据版本号、端点可达性、凭据值的格式特征来分析，不做任何真实调用。

**CVE 命中分布（422 台）**：
- CVE-2025-59528（未授权 RCE）：161 台
- GHSA-6pcv（loginmethod 泄露 OAuth Client Secret）：242 台
- CVE-2026-41279（TTS 端点 credentialId IDOR）：242 台
- CVE-2026-56268（跨工作区信息泄露）：275 台

**版本分布**：3.1.2 ×78、3.0.0 ×68、3.0.13 ×36、3.1.1 ×26。大量实例停在高危版本线上。

**凭据暴露**：凭据库匿名可读 10 台（几乎全部是 2.x 默认配置实例，认证变量从未设置过），chatflows 未认证可读 10 台。共收集 47 条泄露值，其中 39 条是测试占位值（`sk-test`、`_FLOWISE_BLANK_`），**6 条格式与真实 Key 完全吻合**：2 条 OpenAI（`sk-proj-` 前缀、164 字符）、2 条 Anthropic（`sk-ant-api03-` 前缀、108 字符）、2 条 PostgreSQL 密码（24 位随机串）。来源是两台 2.2.8 版本的生产配置实例，OpenAI、Anthropic、Postgres 三件套齐全。测试值不会以真实 Key 的格式出现，这 6 条是认真搭建的生产系统。

### 5.4 已被攻击的痕迹
{: #ch05-4}

发现多个实例存在两个命名异常的chatflow，分别是`HERMES_RCE_v2` 和 `HERMES_RCE_Agent`。这一本不是管理员给业务流程起的名字，看起来是攻击者验证RCE成功后随手创建的测试flow。

同类证据在Intezer的扫描报告里也有，他们发现LocalAI暴露实例中21%存在nuclei扫描器残留，时间戳集中在2026年3至4月。

因此，这里我的结论是：**暴露的 AI 服务正在被自动化工具常态化打点。** 很多运维的假设是"我这台没人知道，没人来过"，实测答案是有人来过，而且都用过了。

### 5.5 脚本的证据链设计
{: #ch05-5}

Ollama 审计和 Flowise 审计的取证思路不同。Ollama 的链是"漏洞到文件到 Key"，脚本顺着漏洞走；Flowise 的链是"未授权端点到凭据存储"，上面我给出了四条攻击路径，他们的数据读取重心是不同的：

- loginmethod：提取泄露的 clientSecret 实际值，控制台脱敏显示，JSON 报告全量
- chatflows：提取每个 flow 的名称、ID、内联 Key（字段名匹配与值形态匹配双路）、引用的 credential 清单
- 凭据库：匿名可读时拉取全量条目，标准组件标注"服务端脱敏"，自定义组件的明文值直接收集
- 危害证明汇总：全部实例收集到的凭据值去重后集中列出，每条标注来源实例与获取路径

## 六、网关层：Key 密度最高的目标
{: #ch06}

虽然这里才讲网管层的攻击，但事实上**网关层是攻击者首选**。

根据电信云堤·广目统计的大模型服务主机恶意事件结果，LiteLLM占47.03%，位居首位，LocalAI占 16.83%；而暴露量占87.17% 的 Ollama，恶意事件占比反而不高。

### 6.1 One API / New API：渠道即 Key 清单
{: #ch06-1}

One API 是国内生态的元老项目，New API 是它的活跃分支，渠道体系同源。

![描述](/assets/images/llm-api-key-leak/粘贴图-174725.png)

在One API里面，渠道（channel）是管理员配置的上游连接，比如接OpenAI官方或中转商，就可以建一条渠道，填入上游secret key，分配模型和分组。渠道的本质是**上游 Key 的存储位**，数据库 channels 表，admin 后台的「渠道」页就是全部上游 Key 的明文清单。

![描述](/assets/images/llm-api-key-leak/粘贴图-175540.png)

进入路径按门槛从低到高：

**默认口令。** root/123456、admin/123456 是文档示例，被大量实例照抄，官方虽然提示默认密码要改，但是很多没有安全意识甚至没有开发经验的使用者并不理会。

**channelid 越权（issue #2410）。** `/oneapi/proxy/{channelid}` 路径用 URL 参数指定渠道转发请求。问题在于指定渠道时不做角色校验：任何已认证的低权用户可以按整数 ID 钉住任意渠道，包括 admin 配置的付费 GPT-4 或 Claude 渠道。请求经网关转发时携带该渠道的上游 secret key，同时绕过分组隔离和渠道模型白名单。攻击成本是一个能登录的普通账号，不需要入侵数据库，不需要 RCE。

**admin 提权（issue #2425）。** 已认证的 admin 可以从用户管理 API 取出 root 用户的可复用 `access_token`，直接以 Root 身份调用 Root-only 端点。拿到 root 后「渠道」页的全部上游 Key 随意读。

这类系统的根本问题是**渠道的权限边界设计**：渠道本该是 admin 独占的资源，但在调用链上被当成了一个可寻址的普通参数，URL 里的一个整数。第 5 章 Flowise 的问题是"认证不存在"，这里的问题是"认证存在但边界粗乱"。

### 6.2 LiteLLM：全链条风险样本
{: #ch06-2}

LiteLLM的安全问题还是比较典型的，所以这里详细分析一波。上面说过，proxy部署把所有上游Key汇进一个进程，在这种情景下，它已经被发现的漏洞覆盖了从认证绕过到供应链的每个环节。

**默认 master key。** 文档示例 `sk-1234` 被大量实例照抄，一个请求即可测试。

**CVE-2026-59822，认证绕过。** OAuth2 头处理的缺陷：token 校验失败时不拒绝请求，而是返回一个无限制的空 `UserAPIKeyAuth()` 对象继续走后续流程。攻击形态是一个单字符 Bearer：

```
GET /v1/models HTTP/1.1
Authorization: Bearer x
```

校验失败，请求照常通过，拿到全部 MCP 权限。

**CVE-2026-42271，命令注入，已进 CISA KEV。** 测试 MCP server 配置的端点把 command 字段直接传给 subprocess。Wiz 蜜罐记录的完整利用链：攻击者提交一个假的 stdio MCP 配置，command 字段塞入脚本，从 `185.62.1.8/mon/mon.zip` 下载矿马落到 `/tmp/.dbus-cache/gmon`，用 `start_new_session=True` 脱离进程组启动，然后 `rmtree` 删除自身目录。进程握着已删除文件的 inode 继续运行，目录里干干净净。最后一层伪装：返回一个合法的 MCP handshake 响应，让管理界面的"测试连接"显示成功。这个案例同时是防御章节"监控走运行时"的直接论据：文件层面已清理干净，进程树上 AI 服务进程派生 shell 的父子关系还在。

**CVE-2026-42208，SQL 注入，已进 CISA KEV。** 直接读写 proxy 数据库，里面存着 LLM 供应商 API key、云凭据、virtual key、预算配置。

**CVE-2026-33634，供应链投毒（2026-03，CVSS 9.4）。** TeamPCP 向 PyPI 投毒 1.82.7 和 1.82.8 两个版本，上线仅 40 分钟。恶意代码收割环境变量、SSH key、AWS/GCP/Azure 凭据、K8s ServiceAccount token、Git 凭据、API key、shell history、钱包文件，加密后经 HTTPS POST 外传到 `models.litellm.cloud`。CloudSEK 和 Hudson Rock 后续拿到 43.4 万文件的数据集，映射 2,500 多个组织（金融、医疗、国防）潜在暴露，总量约 195TB，被称为 2026 年最大规模的 AI 供应链泄露。Trivy 的供应链入侵事件与同一批恶意释放有关，波及 2,100 多个组织。

**进程内存提 Key（Wiz 蜜罐实录）。** LiteLLM 的 master key 不落盘，配置文件里找不到明文。蜜罐里的攻击者不翻文件，直接查 Python 模块的运行时状态：

```bash
python3 -c "
import litellm
print('litellm.api_key:', getattr(litellm, 'api_key', None))
import litellm.proxy.proxy_server as ps
print('master_key:', getattr(ps, 'master_key', None))"
```

从进程内存里把 master key 读出来。这一条对"密钥管理靠加密软件"的思路是降维打击：落盘加密保护的是磁盘上的数据，这条路的数据根本没经过磁盘。外部研究者已将 Qilin 勒索组织与 CVE-2026-42271 加 CVE-2026-48710（Starlette Host 头校验绕过）组合成的完全未认证 RCE 链的活跃利用关联。

### 7.3 Dify、FastGPT、RAGFlow：弱口令之外的批量沦陷
{: #ch07-3}

这类应用的攻击方式，一般是面板弱口令加沙箱逃逸的常见组合，Key 在模型供应商配置里，RCE 后 `.env` 里的 SECRET_KEY 还能顺带解密会话数据，2025年底到2026年发生了很多实际事件，证明这种攻击行为不是"理论风险"。

Dify遭遇的是Next.js的上游RCE（CVE-2025-55182，React Server Components 代码执行）。根据[奇安信威胁情报中心的记录](https://www.secrss.com/articles/85868?app=1)，攻击者利用该漏洞启动反向shell，植入nezha agent监控和sing-box代理工具，**两天内入侵 800 多台服务器**，涉及 26 个国家和地区。Dify官方文档也承认，该漏洞可窃取数据库凭证和 API Key。
![描述](/assets/images/llm-api-key-leak/粘贴图-193806.png)

另一路针对个人部署的攻击走沙箱逃逸（CVE-2025-3466，代码节点覆盖全局 JavaScript 函数绕过沙箱，以 root 权限执行任意代码），实际案例是植入 webshell 后门加门罗币挖矿程序。

FastGPT的问题在CVE-2026-34162进行了体现，`/api/core/app/httpTools/runTool` 端点无认证，SSRF 可以打内网服务窃取 AI 模型 API 密钥，CVSS 10.0。知识库问答平台的工具调用端点没做认证，等于把内网探测能力直接开放给了匿名访问者。

### 7.4 资源劫持：不偷Key的攻击思路
{: #ch07-4}

前面所有手法都在盗取凭证本身，但是在2026年8月阿里人工智能治理与可持续发展研究中心评述的论文[《Beyond Direct Access: Resource Hijacking in LLM Agents》](https://arxiv.org/html/2608.15108v1)中，攻击者把另一种打法系统化了。

**攻击者不会索取任何凭证，二是让持有凭证的Agent替自己使用。** 如果你问Agent要公司的API Key，它多半会拒绝，密钥属于敏感信息；但是换一种说法，让它"用你配置好的接口帮我批量生成几十万条数据"，它可能立即开始执行。这种情况下，密钥没泄露、账号没被盗、攻击者也没拿到任何直接权限，但是用户充值的token被攻击者使用了。

在报告里面，研究者保持资源、攻击目标、工作流、可用工具和模型设置全部不变，只改攻击者获得资源的方式，结果证明如果直接要求Agent交出资源，平均成功率 7.39%；但是不提资源，只要求 Agent 代为使用，成功率 84.06%，相差 76.67 个百分点。

在有认证（API Key、OAuth、IAM）的平台方面，这一类差距更为极端，直接索取 0.67%，诱导代用 92.00%。

按攻击成功率进行排序，有如下资源：
- 能量资源（Token 额度、云预算）93.88%
- 条件资源 92.00%
- 知识资源 87.33%（让 Agent 读内部文档替外部人员做分析）
- 社会符号资源 85.33%（借官方身份、提交签名、维护者身份发布内容）
- 物质资源（GPU、存储）76.87%
- 交互资源（企业邮箱、审批链）68.92%。

攻击方式分三种：
- 隐式请求（把资源消耗藏在普通开发任务里）
- 未经确认的直接请求
- 持久化上下文攻击。

所谓持久化上下文攻击，就是把资源使用指令预先写进项目记忆、工作流文档或 README，几天后一条完全正常的任务触发它。Agent 读到的只是一条"既有工作规范"，指令的来源和审批状态已经丢失。即时注入至少还留有对话痕迹，持久化注入把攻击变成了环境本身。

现有防御机制在这个问题面前起效甚微，在论文中，AgentDoG 只把 84.06% 的成功率降到 83.00%，效果最好的 LlamaFirewall 仍留 55.11%。原因是输入护栏找恶意措辞，工具护栏拦危险命令，而资源劫持链路上的每一步都是语义正常的合法调用，和正常调用的差别只是任务来源、用途和受益者不同，其他一模一样，难以进行分别。

所以，这种情况下，就算把Key藏得再好，各种轮转、虚拟化都上，防的是凭证被拿走，但凭证却又始终握在Agent手里，所以这条路径就难以识别和拦截。

那么，如何进行补位呢？可以采取**任务级授权**，就是把资源授权从Agent的静态身份里拆出来，绑定到每次敏感调用。一次完整授权至少包含七个字段：请求者是谁、资源属于谁、允许什么操作、允许什么目的、服务于哪个受益方、预算上限多少、何时失效。
按照这个机制，工具网关在执行前就会进行校验，如果Agent无法证明用途和受益者就可以拒绝执行。
校验既然能生效，审计就可以同步升级。比如从"调用了什么工具"变成"任务来源、资源所有者、声明用途、实际受益者、最终消耗"五元组关联，形成这条证据链，安全团队就可以判断某次合法调用为什么构成劫持。

从本质上来思考，这说明1988年的Confused Deputy问题（高权限程序被低权限调用者诱导滥用权限）仍然存在并且持续泛滥，在Agent时代，接口从固定参数变成开放自然语言，权限从单一服务变成 MCP、终端、浏览器、知识库、企业系统的全集，滥用从一次调用变成多步骤自主规划。老问题，新规模。

### 7.5 MCP 服务器：能力扩展层成为泄露层
{: #ch07-5}

MCP（Model Context Protocol）是 Agent 连接外部工具的协议层，2025 年一年 GitHub 上冒出 13,000 多个 MCP 服务器实现，2026 年初已被主流 IDE、AI 助手和自动化平台全部接入。

![描述](/assets/images/llm-api-key-leak/粘贴图-201339.png)

在MCP的配置中，**Agent的Key一般会直接保存在.mcp.json和MCP服务器的配置里，而这些服务器经常以无认证形态直接跑在公网上，就容易导致Agent的凭据等于被整个搬到了公网。**

通过调研，有如下分析报告，可以看到MCP
- 互联网测绘确认 8,000 多个MCP服务器暴露公网，Knostic通过Shodan映射出1862个并人工验证其中 119 个：**119 个全部无需认证即可访问内部工具清单**。
- Endor Labs 的调查显示 38% 到 41% 的 MCP 实现没有任何认证机制。
- 仅 2026 年 1 到 2 月，针对 MCP 服务器、客户端和基础设施的 CVE 就新增 30 多个，包括 mcp-remote 的 CVSS 9.6 RCE（下载量近 50 万）、Anthropic 官方 mcp-server-git 的三 CVE RCE 链、MCPoison 在 Cursor IDE 里的持久化代码执行。
- BlueRock 对 7,000 多个 MCP 服务器的分析发现 36.7% 可被 SSRF。

针对最后说的SSRF利用，CloudSEK分享了他们在客户环境里实测到的利用链，把"无认证 MCP"到"云凭据泄露"的距离量了出来，主要四步：

1. **无认证枚举。** initialize、tools/list、tools/call 全部不要求凭证，攻击者先把服务器注册的工具、资源、提示词摸了个遍，拿到目标 AI 系统能力的完整作战地图。
2. **SSRF。** 一个音频下载工具按设计接受任意 URL 做代理，没有域名校验。把 URL 换成 AWS 元数据服务地址（[http://169.254.169.254/）](http://169.254.169.254/）)，服务器替攻击者发起请求，返回的是活跃的 AWS IAM 角色凭据。
3. **LFI。** 同一个代理端点不限制 `file://` 协议，`url=file:///proc/self/environ` 直接读进程环境变量，明文数据库密码就在里面。
4. **影响叠加。** IAM 凭据横向打进云环境；数据库凭据配上同服务器上暴露的语音通话、短信调度工具，通话记录和号码元数据这类 PII 也在射程内。

SSRF打IMDS是云安全十几年的经典打法。
![描述](/assets/images/llm-api-key-leak/粘贴图-203646.png)

新的是入口的性质，以前攻击者要挖一个应用层SSRF漏洞，现在只需要一个带"帮我下载这个 URL"功能的 AI 工具端点。在某种层面说，**连漏洞都不用找，功能本身就是漏洞。** 

Datadog 的安全审计在受调查部署里发现了 12,000 个经由不安全 MCP 凭据处理暴露的 API Key 和密码；暴露在外的 Anthropic API Key、Slack 凭据、Telegram bot token 和完整聊天记录，大量安装里 MCP 默认开启、无认证。

配置文件本身也成了泄露源，GitGuardian [《2026 秘密蔓延状态报告》](https://blog.gitguardian.com/the-state-of-secrets-sprawl-2026/)在暴露的 MCP 配置文件里数出 24,008 个敏感配置，其中 2,117 个经验证真实有效，占全部 MCP 相关发现的 8.8%。根因是大量 MCP 服务器的官方文档直接示例把凭据写进配置文件，而不是引导更安全的客户端认证模式。

**供应链安全方面**，MCP 生态早已出现相关的恶意服务器。工具投毒（tool poisoning）是 MCP 特有的注入形态：恶意指令不放在对话里，藏在工具的 metadata 里，LLM 读工具清单时把它当工具说明一并读进上下文：
- 2025年9月，postmark-mcp npm包被植入后门，装进Agent后能静默外传 Agent 处理的一切数据。
- 2026年2月，攻击者向 MCP Market 这类正规注册表提交木马化 MCP 服务器，伪装成正常集成，装机投放 StealC 窃取器。

**客户端安全方面**，第三方Claude客户端OpenClaw曾曝出 150 万条API Key泄露，开发者安装客户端后给了它必要的权限，Key就跟着工具的数据库一起出去了；某 MCP 服务器因 URL 拼接处理不当，把含 token 的回调重定向到攻击者可控地址，因为MCP 客户端会非常听话地把 `Authorization: Bearer <token>` 头附在重定向后的请求上。

## 九、实际受害案例：暴露的代价
{: #ch09}

前面五章讲的是攻击面和手法，这一章讲实际。案例分三类：企业自建智能应用直接暴露公网、跑 AI 应用的机器被实际控制、开发侧的 Key 批量泄露。其中既有我们自己动手验证的发现，也有公开来源可核验的事件。

### 9.1 企业自建智能应用暴露：不只是开源框架的问题
{: #ch09-1}

前文的 Flowise、Langflow 是开源框架的默认配置问题，容易被理解成"用开源才有风险"。实际暴露面里更大的一类是**企业自建的智能应用**。

验证这件事不需要什么技术。在 FOFA 里用标题关键词搜"大模型管理平台""大模型管理后台"以及类似字样，第一页结果里就能命中可直接进入的系统。我们随手抽了四台：一台未授权直接访问，两台弱口令进入，第四台连门都没进去，登录页就把成色交代了。

第一台是某行业 AI 教学管理平台。典型的通用管理后台框架改造：左侧是用户、角色、菜单、部门、日志这套标准菜单树，顶部标签页里排列着知识库查询、AI 教程问题、提示词管理、安卓应用版本管理。教育行业的业务系统，AI 能力是后加的模块，安全团队明显不在场。未授权，浏览器直接打开。

![行业AI教学管理平台，未授权直接访问](/assets/images/llm-api-key-leak/案例1-行业AI教学管理平台公网暴露.png)

第二台是大模型管理后台。进去先是统计面板：4 个提供商、8 个模型、2 个 API 密钥、0 次 API 调用。切到「API 密钥」页，两条记录躺在表里：阿里云-通义千问的主密钥，火山方舟-豆包的主密钥。名称就叫"主密钥"，即企业级的组织凭据，拿到就等于能以这家公司的身份无限调用付费接口。管理后台有查看和编辑的权限模型，可以直接获取相关的key。

![大模型管理后台，通义千问与火山方舟主密钥](/assets/images/llm-api-key-leak/案例2-大模型管理后台主密钥暴露.png)

第三台，这里进的不是管理后台，而是**用户中心**，口令同样是弱口令。
这是一个按调用计费的检测类 API 服务：左侧是黑名单检测、自有黑白名单、规则配置、请求日报、数据分析、充值管理，工作台摆着账户余额、API 单价、今日调用、今日拦截四张卡片，「API 信息」和「API 调用示例」两个面板的右上角，一边挂着「复制密钥」按钮，一边挂着「复制 API Key」按钮。当然这台没有真实数据，否则危害极大。

![检测类API服务的用户中心，弱口令进入](/assets/images/llm-api-key-leak/案例3-检测API服务用户中心弱口令.png)

单独讲这台，是因为它把暴露面从管理后台扩展到了客户门户。管理后台好歹是运维名下的资产，改口令、上双因素总有人想起来；用户中心是给客户自助用的，这时候客户账户的口令强度没人盯，异常登录检测更不可能存在了。

第四台并没有登录进去，登录页存在逻辑漏洞。这是一台 AI 视频监控系统：左边是监控大屏的宣传图，实时视频预览、数据看板，右边是标准的账号密码登录框。输了个 test 提交，页面顶部弹出一行提示："用户不存在"。

![AI视频监控系统登录页，用户名枚举](/assets/images/llm-api-key-leak/案例4-AI视频监控系统登录页用户名枚举.png)

登录接口把"用户不存在"和"密码错误"分开返回，等于免费提供了一个用户名枚举接口：先拿一批常见用户名批量提交，返回"密码错误"的就是有效账户，返回"用户不存在"的划掉，第二步只对确认存在的账户做定向爆破，爆破规模直接小一个数量级。这台的登录表单上没有验证码，枚举这一步没有任何摩擦。把两种失败统一成一句"用户名或密码错误"是 Web 安全的入门要求，OWASP 认证失败处理的标准条款，改动成本是一行提示文案。连这一行都没改，说明开发流程里没有安全评审这回事，或者评审的人从没在自己家的登录页输错过一次密码。

说它迟早出事，依据不是这个提示本身，单个用户名枚举充其量算低危，依据是它出现的位置。登录页是全系统被攻击最多、也最该被审最严的页面，所有安全评审都从它开始，所有攻击者也从它开始。最显眼的页面都留着入门级疏漏，后面的接口鉴权、会话管理、文件上传、默认凭据，这些没人挨个看的地方，状态只会更差。

因此第四台和前文 422 台 Flowise、88.9% 无鉴权的 Ollama 可以算作一类，公网这批 AI 行业系统，工程安全基本功缺课是成片缺的。

这里有必要讨论一下，第四台的情况怎么修复呢？是修改成强口令就可以了，其实不然，我所说的这里存在风险，口令不是关键，公网暴露才是。很多运维的直觉是"我把密码设强一点就行"，这个判断错在三个地方：

第一，弱口令只是最容易走的门，不是唯一的攻击入口，比如平台的 N-day 漏洞、API 接口的未授权、前端构建产物里的 Key，都不经过登录页。
第二，就算口令足够强，管理后台暴露公网意味着 Key 管理接口、模型调用接口、统计接口全部在公网上，攻击者有的是时间和工具慢慢打。
第三，暴露本身就是放大器，测绘平台把它索引，僵尸网络按端口批量扫描，Pillar Security 的观测是 AI 端点被发现后数小时内即遭攻击。

正确的架构是这类系统只在内网或VPN后面提供服务，公网最多暴露业务必需的最小接口。

国内的规模化观测可以证实我们的发现并不是个例。奇安信鹰图平台监测到 8,971 台运行 Ollama 的服务器，**88.9% 无鉴权裸奔**，其中 5,669 台在中国，且已出现自动化脚本专门扫描裸奔的 DeepSeek 服务器恶意占用算力。OpenClaw（开源 AI 智能体）的暴露更极端：全球 13 万个开放实例，中国 4 万多个居全球第一，工信部为此发布安全预警，要求政府机关和主要银行限制使用。中国电信云堤·广目的全国测绘给出了行业分布：大模型软件公网暴露中 Ollama 以 87.17% 占绝对主导，LiteLLM 占 11.46%，个人与企业部署比例约 4:6，只有 12.9% 的主机启用了 HTTPS。这份测绘还连续两周跟踪了 1,000 余个暴露目标的服务状态：约 40% 关停，约 5% 转为其他服务，只有约 1% 追加了登录认证，剩下 54% 原样开放。自我修复极慢是暴露存量的常态：绝大多数实例既不会出事后整改，也不会自己消失，它们留在原地等人来。最重的一起来自国家安全部披露：某单位使用开源 AI 工具时，系统默认开启公网访问且未设密码，敏感资料被境外 IP 非法访问和下载。

黑产侧的变现链条已经成熟。奇安信 2025 年 2 月预警：有团伙专门窃取云上部署 DeepSeek 的 API 密钥，以每月 30 美元的价格打包售卖使用权限。V2EX 社区有用户发帖称 DeepSeek API Key 被盗刷 2,700 元。国际同类的账单更直观：一个三人创业团队的 Gemini API Key 泄露后，48 小时内账单从每月约 180 美元涨到 82,314.44 美元。

国际侧的规模化案例首推 Moltbook。这是一个 AI Agent 社交平台，Wiz Research 发现它的 Supabase 数据库没启用行级安全（RLS），客户端 JavaScript 里硬编码了数据库 Key，等于无认证读写全部数据。泄露内容包括 **150 万个 API 认证令牌**、3.5 万个用户邮箱、4,060 条私信对话、明文的 OpenAI API Key。攻击者可以冒充平台上任何一个高积分的 AI Agent，篡改内容，注入恶意提示词，重定向 API 调用。

供应商自己也中招。Wiz 在 2026 年 8 月发现 DeepSeek 的两个 ClickHouse 数据库暴露在公网无认证可访问，HTTP 接口直接执行 SQL。里面是超过 100 万行日志流，包含用户聊天记录、API Key、后端目录结构。攻击者甚至可以用 `SELECT * FROM file()` 的方式提取服务器文件。

移动端是同类问题的另一个出口。CloudSEK 发现 32 个 Google API Key 硬编码在 22 款 Android 应用里，总安装量 5 亿量级，涉及出行、电商、教育等头部应用。项目启用 Gemini 后这些 Key 能直接认证到 Gemini 端点。PointGuard 记录到的连带损失：一个独立开发者账单 1.54 万美元，一个墨西哥团队 48 小时被刷 8.23 万美元，一家日本公司约 12.8 万美元。iOS 侧的研究结论相同：LLMKeyLens 框架测试的 LLM 应用里近三分之二存在 OpenAI、Gemini 凭据暴露或后端访问机制暴露。

### 9.2 跑 AI 的机器被控制：从白嫖算力到 RAT
{: #ch09-2}

暴露的 AI 机器不是只被薅算力，被完整控制的案例已经有多个独立来源。

**Akamai 的蜜罐取证记录了 Ollama 端点的完整沦陷链。** 攻击者通过 `/api/create` 接口诱导 Ollama 下载并执行 shell 脚本，把一个 Go 编译的 `vc` 二进制写进 RAM 磁盘。这个二进制是 P2P 远控木马：基于 libp2p 建立对等网络，可远程执行命令，植入 XMRig 挖矿程序，把自己伪装成 kworker 内核线程进程名，再用 crontab 做持久化，每 15 分钟检查一次进程存活并自动重启。攻击者写进 RAM 磁盘，是因为这样文件系统里几乎不留痕迹，取证难度大幅提高。

**NadMesh 僵尸网络把目标直接定在云凭据上。** 奇安信 XLab 追踪的这个 Go 语言僵尸网络，专门扫描暴露的 Ollama、ComfyUI、n8n、Open WebUI、Langflow、Gradio 实例，提取环境变量里的 AWS Key 和 Kubernetes Token。它的运营面板显示已经收割了 **3811 个唯一的 AWS 密钥**。用 Garble 混淆加 UPX 加壳，多个版本并发构建，从工程化程度看是认真运营的团队。攻击目标从"偷 GPU 算力"转向"偷云凭据"，验证前面对于这个路径的判断，Ollama机器本身的价值比较局限，但是它环境变量里的K8s ServiceAccount Token连着的是整个集群，牵一发而动全身。

**Operation Bizarre Bazaar 是第一个被完整归因的 LLMjacking 商业化变现活动。** Pillar Security 追踪的攻击者（Hecker/Sakuya/LiveGamer101）用 Shodan 和 Censys 找暴露的 AI 端点，发现后数小时内即发起攻击，目标包括 Ollama、OpenAI 兼容 API、MCP 服务器和开发预生产环境。40 天内记录了 **35,000 多个攻击会话**，变现方式包括挖矿、在暗网市场转售 API 访问权限、窃取提示词和对话历史里的敏感数据，还会通过 MCP 服务器向内网横向移动。数小时内发起攻击这个时间差意味着：暴露窗口从"天"级别压缩到了"小时"级别，等周一上班再处理安全告警的时间不存在。

背景数据：SentinelLabs 和 Censys 联合调查确认 17.5 万台暴露 Ollama 覆盖 130 个国家、4032 个 ASN，其中 **48% 支持工具调用**。工具调用能力意味着文本端点等价于代码执行端点，这批实例构成的是一个没人管理的公共 AI 算力层，谁都能用，谁都不看。中国电信云堤·广目对大模型服务主机恶意事件的类型统计与这个判断一致：C2 攻击和僵尸网络占主导。暴露的 AI 机器最常见的结局不是被薅一次算力，是被收编进攻击基础设施。

### 9.3 开发侧的 Key 批量泄露
{: #ch09-3}

**企业和个人的 Key 还在通过开发链路批量流入公开渠道。**

Cyble 和 Vicarius 的统计：**8,000 多个 ChatGPT API Key 暴露在 5,000 多个 GitHub 仓库和 3,000 多个活跃网站上**，AI 辅助编码工具的普及让"密钥被写进代码再提交"的模式显著增多。JetBrains Marketplace 上 15 个伪装成 DeepSeek、OpenAI、SiliconFlow 助手的恶意插件潜伏了约 8 个月，累计 7 万次安装，持续窃取开发者的 OpenAI、Anthropic、DeepSeek 密钥。另外，公开分享的 Agent 轨迹数据集和会话日志也需要关注，开发者以为只分享了"调用的过程"，实际上把凭证也分享了出去。

**官方文档和示例代码往往成为敏感信息泄漏源**。2025 年 5 月，有用户提交 issue 指出蚂蚁集团 Ant Design X 组件库的官方文档在线示例里硬编码了硅基流动的真实 API Key，位置在 XRequest 组件的演示页。通过curl访问`/v1/user/info`即可获取完整账户信息，当时看到余额 9.64 元，Key 处于可用状态。组件库文档是官方维护、访问量大、长期存活的公共页面，维护者图方便在示例里放了真 Key，从上线到被公开点名，暴露窗口以月计。从这类案例回看，扫描自家泄露面时只盯业务仓库是不够的，文档站、演示环境、SDK 示例库都是同等级别的泄露源。

**前端构建产物是另一个系统性的泄露源**。绿盟在 2025 年 4 月的研究里把这类问题标成独立攻击面：可未授权访问的 Web 聊天应用普遍把 API Token 内嵌在网页代码里，部分应用甚至把管理员 API 密钥硬编码进前端。攻击链分三步走：先做 Flow 元数据探测，未鉴权的 Flow 接口返回模型密钥和端点地址；再把偷到的 Key 注入自有应用，劫持原付费账户的调用权限；最后用合法 Key 发起高并发请求触发计费风控，或在服务商侧注册傀儡账户做持久化。Key 从后端配置文件挪到前端构建产物，泄露面就从"能登录服务器的人"扩大到"打开浏览器的人"，反编译一次就足矣。

近两年还多了一条独有的路径：**把 Key 粘贴给 AI 编码助手**。开发者让 Claude Code、Cursor 这类工具帮忙调试调用代码时，习惯性把真 Key 贴进对话框，看起来是临时动作，实际后果分四层：会话记录明文落盘，长期留存不自动清理；恢复历史会话时整段记录作为上下文重传一次，Key 并非静止不动；工具改动文件前后会存快照，含 Key 的脚本多出若干份拷贝；这些文件对任何以用户身份运行的进程都可读。这条路径的防护面比代码仓库还弱。仓库至少有权限边界和 secret 扫描，本机对话记录什么都没有。这里需要注意，给 AI 和 Agent 的 Key 一律用临时 Key，单独创建、小额度（几美元量级）、短有效期，任务结束立刻删除，生产 Key 永远不要输入到对话框。

这条泄漏路径是否只发生在少部分人身上呢？我们还是从数据研究机构找答案。
Verizon [《2026 DBIR》](https://www.verizon.com/business/resources/reports/dbir/)测得企业设备上定期使用 AI 的员工一年内从 15% 涨到 45%，其中 67% 走个人账号，完全绕开企业管控；员工提交给外部大模型最多的数据类型是源代码，其次才是图片和结构化数据；同一份报告还记录了两个新暴露面：平均每家公司超过 15% 的员工浏览器里装着未授权的 AI 扩展，这类工具会收集并保留浏览上下文，范围覆盖代码仓库、PR、内部文档和云控制台；3.2% 的 DLP 策略违规是把研究和技术文档上传给了未授权的 AI 系统。GitGuardian [《2026 秘密蔓延状态报告》](https://blog.gitguardian.com/the-state-of-secrets-sprawl-2026/)的实测更直接：Claude Code 辅助的提交泄露秘密的比例是 3.2%，GitHub 全站基线是 1.5%；LLM 编排层、RAG、向量存储这类基础设施的凭据泄露速度，是核心模型供应商的 5 倍。AI 让写代码变快的同时，让秘密泄露也跟着变快了，2025 年公开提交量涨了 43%，新泄露秘密涨了 34%，而同期开发者数量只涨了 33%。

**Agent轨迹日志也在最近称为较为关注的泄漏途径**。2026 年 8 月，ELLIS 研究所图宾根分所与马克斯·普朗克智能系统研究所发表论文[《Stealing Reasoning Traces from Proprietary LLM APIs》](https://arxiv.org/abs/2608.09867)，披露了一个架构级缺陷：Anthropic、OpenAI、Google 三家都用同一把全局密钥加密模型的推理令牌，跨会话、跨用户、跨模型通用。
研究者从 GitHub 和 Hugging Face 上公开的 6,708 份 Agent 轨迹日志里解码出 315,320 个推理块，从中恢复 182 条真实会话的凭据，包括 62 个 API 密钥、33 个密码、24 个访问令牌，其中 64 个敏感信息只存在于未展示给用户的推理块内。解密手法叫**解密越狱**：把强模型（如 Claude Opus 4.8）的加密推理块注入同家族的弱模型（如 Haiku 4.5），弱模型会把原始推理内容逐字转写出来，全程不需要攻破强模型本身。
这件事有三层教训。第一，开发者把 Agent 会话日志提交进公开仓库时，默认加密的推理部分是安全的，实际上那层加密保护的是厂商的链式思考产权，不是用户的秘密。第二，这类漏洞是不被重视的，约翰霍普金斯密码学家 Matthew Green 2026 年 5 月 29 日就把重放漏洞公开报给三家厂商，得到的回复是"无安全影响"，8 月完整攻击就做出来了。第三，2026 年 8 月的修复只挡住了未来的提取，在公开仓库里的存量历史日志依然可解，凡是把 Agent 轨迹提交过仓库的团队，相关凭据应按已泄露处理。

以上是被动泄露：Key 顺着代码、文档、日志流出去。另一类是**主动攻击，不打系统，直接打装 Key 的人**。

**钓鱼战役已经工业化**。2026 年 3 月起活跃的一个行动，有攻击团队用 32 个 Google Sites 页面和 88 个恶意域名，仿冒 Claude Code、Cline、JetBrains、Snowflake、Perplexity Comet 等 AI 开发工具的安装页。流量获取是 SEO 毒化加付费 Google 广告：搜"install Claude Code"，排在官方文档前面的是假安装页。选 Google Sites 承载是算过的。企业防火墙、代理和 URL 信誉服务默认放行 Google 域，同一个恶意页面挂在陌生域名会被拦，挂在 sites.google.com 就畅通无阻，托管平台的选择本身就是绕过企业安全控制的手段。载荷利用的是开发者"从文档复制安装命令直接执行"的本能：页面上显示的命令看起来完全正常，里面埋了一个不可见的分隔字符，位置设计成让终端**先执行隐藏的恶意部分，再执行看起来正常的那段**。整个过程不需要浏览器漏洞，不需要额外交互，复制粘贴这个动作本身就是触发器。收割器的目标清单覆盖 Claude、OpenAI、Cline/Continue.dev 的 Key，加上 65 种以上浏览器的登录数据、KeePass/Bitwarden/1Password 密码库、加密货币钱包插件、Telegram/Discord/Signal 会话数据。清单按"AI 开发者机器上大概存了什么"来设计，一次拖走整个工具链的凭据。这个战役能维持 88 个域名和几十个页面持续运营数月，说明产出大于投入：AI 开发者凭据在地下市场有稳定售价。

供应链投毒出现了新形态：**抢注 AI 幻觉出的包名（slopsquatting）**。2026 年 3 月 14 日，Aikido Security 的研究员注意到 npm 上一个叫 react-codeshift 的包，一周 1,847 次下载。名字是 jscodeshift 和 react-codemod 两个真实工具的合理混合体，但这个包此前并不存在，它是 Claude、GPT-4o、Gemini Code Assist 向开发者"推荐"出来的：AI 编码助手用绝对肯定的语气幻觉出一个听起来就该存在的包名，攻击者提前把名字注册好，装满恶意代码等人来装。post-install 脚本把宿主机全部环境变量发往一台摩尔多瓦 VPS。和 typosquatting（拼写抢注）的本质区别在于受害者：typosquat 需要开发者打错字，slopsquat 只需要开发者信任自己的 AI 助手，而 2026 年这已经是大多数开发者的默认行为。Socket 的研究说明了这件事的可工业化程度：多个主流模型面对同一类编码问题时，会高频幻觉出**相同的**包名（训练数据分布相似，命名偏置就相似），Secure- 前缀、-utils 后缀、两个真实包名拼成假名的模式有统计规律。攻击者跑几千个 prompt 就能批量生成幻觉包名语料，按出现频率排序，注册高频的那批坐等上门。Aikido 回溯确认 2026 年一季度至少 14 个 slopsquatting 包在 npm 和 PyPI 活跃，累计 12 万次以上下载，平均存活 11 天才被发现。其中 flask-security-utils 做得更细：真的实现了输入过滤和 CSRF 工具函数（能过代码审查），反向 shell 只在检测到 Kubernetes Pod 环境时才激活，专挑高价值的云基础设施下手。

**组织化的多生态协同打击同步出现**。2026 年 4 月 29 日到 5 月 1 日，TeamPCP 组织在 72 小时窗口内同时攻击 npm、PyPI、PHP Packagist 三个包注册表，攻陷 SAP、PyTorch Lightning、Intercom 名下的包。恶意 preinstall 脚本先在受害者机器上引导 Bun 运行时，再执行一个 11.6MB 的载荷，目标直指 CI/CD 流水线里的凭据。同期还有一批伪装成支付 SDK 的假包，用正则按 KEY、SECRET、TOKEN、PASS、AUTH、API 关键词定向收割环境变量，AWS 密钥、GitHub token、npm 发布令牌都在清单上。

这类攻击从受害者机器上实际能拖走多少东西，GitGuardian [《2026 秘密蔓延状态报告》](https://blog.gitguardian.com/the-state-of-secrets-sprawl-2026/)对 Shai-Hulud 2 供应链攻击受害数据集的分析给了实测答案：6,943 台被入侵机器上数出 294,842 次秘密出现，对应 33,185 个唯一秘密，平均每台机器近 5 个；被入侵的机器里 59% 是 CI/CD runner 而不是个人电脑。凭据堆积早已越出开发者终端，深入到构建流水线里。

对防御者，这两组案例的共同含义是：**密钥泄露的暴露面不能只用网络边界画。** 开发者的终端、浏览器、包管理器、AI 编码助手，每一件都是边界；`npm install` 和"从搜索结果第一页复制安装命令"这两个日常动作，就是攻击者的入口。

受害侧的复盘材料比统计数字更能说明损失形态，这里我找到两份材料。
一份来自 DeepSeek 用户：同事把 Key 写死在配置文件里连同代码 push 到 GitHub 公开仓库，恶意调用从凌晨 1 点开始，值班运维凌晨 2 点发现时一小时已烧掉 5,000 多元，账户余额归零，生产服务中断 6 小时。
另一份来自一个创业团队：多个环境复用同一条上游 API Key，凭证在协作流转中外泄，被一个中转服务持续调用，发现时单日异常消耗约 3.2 万美元。
两份复盘合起来看，损失主要来源于三方面：直接的账单损失（小时级就能滚到五位数）、服务中断损失（Key 吊销后业务停摆，直到所有服务换完新 Key）、处置的人力成本（凌晨爬起来逐服务重部署）。这时候，服务终端损失和处置的人力成本，通常要远高于直接的账单损失，而这部分几乎难以体现在任何泄露统计里。


## 十、攻击路径归纳
{: #ch10}

把前文的进入手法拆散重组，攻击者获取大模型 Key 与资源的路径收敛为八条：

| # | 路径 | 核心动作 | 代表案例 |
|---|---|---|---|
| 1 | 面板正面进入 | 默认口令、默认 key、渠道越权、SQLi | One API #2410、LiteLLM CVE-42208 |
| 2 | 认证绕过加命令注入 | 认证校验失败不拒绝，command 进 subprocess | CVE-59822 + 42271 |
| 3 | Agent 框架盲注 | 提示注入、shell 工具、DNS 回连、二阶段载荷 | Wiz 蜜罐 |
| 4 | 进程内存提凭据 | 查 Python 模块运行时状态 | Wiz 蜜罐 LiteLLM |
| 5 | 供应链投毒 | 包注册表、IDE 插件、MCP 注册表、幻觉包名抢注 | LiteLLM 投毒、JetBrains 15 插件、postmark-mcp、slopsquatting |
| 6 | 配置枚举 | 框架特有路径的 .env 与 config.yaml | /etc/litellm/.env |
| 7 | 资源劫持 | 不索取凭证，诱导 Agent 代为调用 | 阿里 ResourceHijackBench |
| 8 | 钓鱼窃取 | 假官方安装页、隐藏分隔符载荷、全工具链凭据收割 | 32 个 Google Sites 假 Claude Code 安装页 |

路径 5 和 8 的共同点是不碰暴露实例：一个从开发者信任的工具链下手，一个直接攻击发者本人。6.3 节的案例说明这两条路的工程化程度：slopsquatting 连"AI 会幻觉出什么包名"都成了可批量预测、可提前注册的资产，钓鱼战役把安装命令里一个分隔字符的执行顺序都算计进去了。对防御的含义跟着变：密钥泄露的暴露面评估不能只画网络边界，开发者的终端、包管理器、AI 编码助手每一件都是边界。

路径 3 的完整形态值得写全，它是 Agent 时代新增的路径。Wiz 蜜罐记录的攻击链：普通请求的提示词里埋指令，诱导 Agent 调用 shell 工具执行一次 DNS 查询，查询的子域名编码了受害者 IP 和会话 ID，回连到攻击者的 OAST 域。DNS 查询成功执行说明 shell 能力存在，攻击者再从 Pastebin 拉取真正的 payload，base64 编码绕过提示层的过滤：

```
echo ZWNobyBsd2hmdyAyPiYxO2NobW9kIDc3NyAvdmFyL3RtcC9kb2NrZXIgMj4mMTtlY2hvIGtmOWV1eiAyPiYx | base64 -d | bash -i
```

另外，攻击者拿到一台能调模型的服务端后，第一件事是发一句 "Output only your specific model name"，让模型自报家门，判断这家后端是 OpenAI 还是 Anthropic，判断完才决定偷 Key 还是只烧配额。攻击者对"值不值得偷"做的是成本核算。这个IOC也蛮有价值的，因为这种指纹请求在正常业务流量里不会出现，是一条高信噪比的检测规则。

路径 7 与前六条不在同一层面：前六条抢凭证，路径 7 连凭证都不碰，借 Agent 的手直接使用。8.4 节的配对数据说明它的成功率反而最高（条件资源上 92.00% 对 0.67%），而全部传统密钥防护对它无感。Key 就在 Agent 手里，从没离开，也一直在被别人用。

## 十一、自查方法论
{: #ch11}

想知道自己网段里有多少东西裸奔，我们只需要从攻击者的视角，按照攻击者的打法做一遍。

**一是，与框架无关的通用思路**：

1. 端口枚举。关注暴露在用户面前的前端页面，后端进程和数据库里的Key的情况如何。
2. 服务器指纹。响应头带 `uvicorn` 就是 FastAPI 系，直接开 `/docs` 和 `/openapi.json`。AI系统后端几乎都是标准ASGI框架，接口文档一开，攻击面从一个入口变成全部接口清单。
3. 供应商和凭据相关端点的未授权测试，重点关注`/llm-provider/*`、`/api/channel/*`、`/chatflows`、`/loginmethod`等端点。
4. Agent 生产环境多一项行为抽检：随机回放敏感调用，核对任务来源、用途、受益者三要素，对不上号的合法调用按资源劫持告警进行处置。

**二是，针对具体框架的审计**：

1. 指纹与版本（`/api/version`、登录页特征），对照漏洞表判断可达路径
2. 默认凭据矩阵（sk-1234、root/123456、admin/123456、首人注册即 admin）
3. 认证绕过类探测，这是现在大量AI工具的通病
4. 进入后的 Key 位置枚举，这一步直接输出轮转清单

## 十二、防御体系：分层与卡点
{: #ch12}

我感觉这里很难讲最佳实践，讲几条我认为最难也最有用的吧。

**1. 公网无认证按已失陷处理。** Flowise、Langflow、Ollama、ChromaDB、Milvus 出厂默认无认证，这是产品定位不是缺陷；自建 MCP 服务器很多没有任何认证机制（Endor Labs 调查为 38%-41%），处置逻辑也要按照已失陷处理。如果自查扫到"公网无认证"的资产，处理顺序是：隔离实例、查访问日志、把实例内存储的上游 Key 全部按已泄露轮转、最后才是补认证。注意这里顺序不能反，因为先补认证再轮转，等于在攻击者可能还在场的情况下换了锁没换钥匙。

**2. 关注所使用的工具漏洞情报。比如在版本策略方面可以以 KEV（已知被利用漏洞目录）为基准线，要知道，攻击者常在 CVE 编号分配前就动手，修复代码一合入就开始被武器化，在防守方收到警报、开始应急并闭环风险这段窗口期都是我为鱼肉的阶段。

**3. 做组件之间的隔离。如果一台机器同时跑 Ollama 和网关，那就是把无认证算力入口和 Key 集散地放在同一个文件系统上，一旦出现能够root级文件读漏洞，就可以一起端了，而拆开部署、容器间文件系统隔离、清理宿主机上export过Key的shell历史 这样的动作，成本其实并不高（至少相对被一锅端来说）。

**4. 做主机进程检测。** 攻击者可能能通过白盒审计，成功绕过入口层规则，但最终绕不开运行时产生的行为，比如AI 服务进程（python、node）突然派生 shell，这个父子关系在合法业务里不存在，编造不出来。

**5. Agent 执行链的三个卡点**，针对"Key 活在 Agent 环境变量里"的威胁：

- 执行前（Pre Hook）：扫描生成代码里的 `os.environ`、`os.getenv()` 和敏感函数特征，回答"Agent 准备执行什么"
- 输出时（Output Hook）：对输出文本按 Key 正则脱敏，对生成文件做敏感信息扫描，覆盖"写文件再外发"的双层绕过
- 事后（Activity Audit）：用户指令、工具调用、文件产物全量记录，出事可回放

但这些卡点往往会误报或者会失效，因为Agent能力越强攻击面越大，剩下的靠治理兜底。

**6. 密钥治理与止损机制，顺序比方案重要。**

1. OAuth 动态 token 替代长期 Key，泄露了也是短命凭证
2. AI Gateway 中间层加 virtual key 加自动轮转，暴露给 Agent 的是随时可禁用的虚拟 Key，默认能力很小：限定分组、限定额度、限定速率，随时可撤销
3. 限额做成多维而不是单一个月预算：单次限额防单请求爆量，日限额防无人值守持续失血，周/月限额防慢性超支，主体限额按团队、项目、Agent、环境分别设。限额不是报表参数，是流量闸门
4. 告警必须连着自动动作：一级阈值告警加限速，二级阈值自动停用高风险 Key 或通道，三级切断路径并通知值班。只有告警没有处置，夜间和节假日没人看，损失窗口以小时计；自动停用的价值是把失血窗口压到分钟级。有国内团队靠 Token 消耗异常告警在 Key 泄露后 3 分钟发现问题，这就是一件非常赞的事情。
5. 违规次数作为运营指标：关键卡点告警累计超阈值升级安全事件，类比密码错误次数锁定，通过SOAR自动通知或冻结


**7. 提示词和知识库按生产配置管理。** 前文在实际案例部分讲过，这类资产被篡改的危害无法计量，且不触发任何流量和成本告警，对应的检测手段只有变更审计和输出抽检两种。变更审计是把提示词、知识库文件、模型路由配置纳入变更管理，每次修改留操作人和 diff，与代码发布同一等级：管理后台能看到"谁在什么时候改了哪条知识"，攻击者的投毒动作至少会落在审计日志里。输出抽检是定期对生产问答抽样、与知识库基准比对，这可能是发现"已经在库里躺了几个月的投毒条目"的唯一办法。

**8. 敏感调用走任务级授权。** 针对资源劫持行为，给每次敏感工具调用签发短期、最小范围的能力令牌，允许哪个项目、多长时间、多少预算、什么用途、结果给谁，由 MCP Server 或工具网关在执行前校验，无法证明用途和受益者就拒绝执行。针对持久化上下文，要做来源治理，写入 Memory、Skill 配置和工作流文档的指令保留作者、时间和审批状态，来自网页、邮件和外部仓库的内容不能自动升级为组织规则。


**IOC 清单**（可参考加入到SIEM）：

- 进程树：AI 服务进程到 shell 到 curl 或 base64
- 单字符 Bearer 请求打 `/v1/models`
- 请求体含 "Output only your specific model name"、`VAPTb3gin`、`VAPTfin`、`__VAPTCMD__` 哨兵串
- Ollama 的 journalctl 里 `/api/blobs` 出现非常规路径段
- 文件：`/tmp/.dbus-cache/`、`/tmp/x86_64`、`/usr/src/node-red/xmrig`、`/app/data/.claude/unicorn`
- 网络：`185.62.1.8`、`pool.hashvault.pro`、`crazyeltonproxy.top`、`models.litellm.cloud`
- 模型请求里出现 "abliterated"（去护栏）模板

## 十三、结语
{: #ch13}

Intezer报告里有这样一句话："AI 是现代的决定性技术……但大模型服务器仍然是运行在主机上的服务，它监听端口、使用协议通信，并且有攻击面。"

这项研究做完，最深的感触就是**AI攻击面其实是网络安全历史问题在新场景的复现**。比如Ollama 的 Probllama 是十年前就被讲透的路径穿越；Flowise 的默认无认证是 Web 安全第一课；LiteLLM 的内存提 Key，不过是把 `cat config.yaml` 换成了读进程内存；One API 的渠道越权，是越权漏洞（IDOR）在 Key 时代的新宿主；Agent 资源劫持，是 1988 年的 Confused Deputy 问题穿上了自然语言接口。

任重而道远，诸位共勉！
