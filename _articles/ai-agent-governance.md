“公司账号的额度又又又用完了。”

设想公司一位研发同事遇到上述场景后，他会怎样继续处理刚才的代码呢？大概率会换了个人账号，模型效果还是不理想，便改个 API 地址试试别的服务。同事又推荐了一套 Skill，接上能查内部文档的 MCP，原来需要来回复制的材料，现在一句话就能整理出来。

每一步都在解决手头的问题，合在一起，企业采购的工具、个人订阅和自行购买的中转服务就用在了同一份工作里。

销售整理客户记录、财务核对表格、运维排查日志，也可能遇到这样的选择。工具换起来很快，数据处理约定和权限配置却未必跟着调整。

以前把材料贴进聊天框，至少还能看到自己交出去了什么。Agent 接入文件、业务系统和浏览器以后，员工交代的是目标，读取哪些材料、调用哪个工具、把结果写到哪里，可能由它在执行中决定。员工说“整理一下客户周报”，这句话本身并没有说明可以读取多少客户数据，更没有说明可以把原始明细交给哪家服务。

这段没有说清楚的授权，需要企业补上。

员工有权查看一份材料，不代表所有替他处理材料的服务都获准接收它；员工希望完成一项工作，也不代表完成过程中能用到的权限都应该交给 Agent。数据一旦被外部服务接收，事后的告警无法替企业收回那份副本；工具一旦完成发送或修改，只审查最后的回答也来不及。

但这些约束得和工作一起安排。企业工具缺少能力、额度不足或申请太慢，都会让个人工具继续有用武之地。要让受管通道成为员工愿意使用的选择，安全团队就得先知道大家在做什么、为什么这样做，再决定哪些用法可以保留，哪些必须换一条路径。

我们就从这一步开始：沿实际任务查清数据和权限如何被使用，再讨论对话、Skill、MCP 和执行环境各该管到哪里。后面会进一步讨论怎样把这些控制接到不同的 Agent 上，以及客户端、执行环境和企业业务系统如何分工。

## 先弄清员工实际是怎么用的
{: #ch01}

### 从一项工作往下查
{: #ch01-1}

盘点可以先找几个正在使用 Agent 的团队，请员工带着走一遍最近做过的任务。用什么工具只是起点，接下来要看输入从哪里来、经过哪些服务、结果交到哪里，以及这一路用了谁的权限。拿一次真实操作核对，往往比让员工填写一长串产品名称更容易发现遗漏。

![传统自动化与 Agent 工作方式示意](/assets/images/ai-agent-governance/粘贴图-114718.png)

图中强调 Agent 可以在任务中选择工具和后续步骤。传统自动化同样可以包含分支与反馈；企业需要核对的区别，是哪些执行选择交给了模型，以及这些选择受到什么限制。


例如，有员工用企业购买的客户端生成客户周报。深入去分析，模型请求可能走个人配置的 API，报表方法来自社区 Skill，客户数据由本地 MCP 查询，最终文档又写进了个人空间。这里没有哪个产品名称能单独说明整项工作是否合适。判断需要落到具体交接处：这一份数据能否交给下一方，这一次调用是否超出了任务需要。

因此，台账最好能把一项用法记成一条可核对的记录：谁在什么设备或工作区，用哪个账号和请求地址，通过哪些扩展访问什么资源，结果去了哪里。

原有的软件安装清单可以继续帮助发现客户端和进程，任务记录则补上数据流和操作范围。两份记录关联起来，安全团队才能判断某个工具的实际用法。

### 顺着请求，确认谁能接触数据
{: #ch01-2}

企业采购的部分可以先从管理后台核对。哪些员工申请了企业租户，哪些策略已经生效，管理员能取得什么审计记录，都需要实际验收。员工拿到了企业账号，还可能在同一客户端切换身份或配置其他请求通道。至于本地脚本、远端 MCP 和浏览器操作能被后台看见多少，要按产品能力和实际配置验证，缺失的部分再通过终端、工作区和服务端记录补齐。

个人订阅需要同时问清用途和原因。仅用公开资料生成草稿，数据保密要求较低，工具执行权限仍要另查；公司非公开源码、客户明细则不应进入未经企业批准的个人通道。员工付费不能代替公司的数据授权。若企业工具无法完成任务，就要安排可用的替代方案，或明确限定范围和期限的例外，不能只要求员工停用，却不解决工作如何继续。

API 中转还需要向后查一层。公司自建网关、经过评估的供应商和员工购买的转发服务，责任主体与管理条件各不相同。关键是请求在什么位置被解密、由谁处理、又被转给谁。中转服务如果终止 TLS 并处理 API 请求，就可能接触提示词、代码、附件和工具返回；连接有加密，并不能阻止通信另一端读取内容。
![第三方 API 中转服务的商品页面截图](/assets/images/ai-agent-governance/粘贴图-131022.png)

截图展示中转服务的销售形式。商品宣传不能证明其上游模型、数据处理方式或服务质量，采购审查仍需取得可核对的材料。

![社交平台关于中转服务风险的讨论截图](/assets/images/ai-agent-governance/粘贴图-131113.png)

这是一则外部观点截图，其中的指控未在本文核实，不作为中转服务普遍存在相同行为的证据。本文的管控依据是接收方及处理范围是否可确认。


这时要核实服务主体、日志与留存安排、上游账号和路由变化。接口兼容某家模型，不能证明请求一定交给那家厂商，也不能证明适用它的企业服务约定。暂时查不清的路径，应在台账里标为未知，并限制其处理公司非公开数据。域名本身不足以证明服务恶意，缺少证据也不能填成“已确认安全”。


### 再看它拿着什么权限做事
{: #ch01-3}

模型通道查清以后，接下来关注员工使用了哪些AI工具。

![MCP 与 Skill 的概念对照图](/assets/images/ai-agent-governance/粘贴图-142018.png)

这张外部示意图帮助区分工具接入与任务方法。具体客户端的加载流程未必与图一致，Skill 也可能包含可执行脚本，二者都需要核对实际权限。


Skill 可能提供操作指令，也可能带脚本和依赖；MCP 把工具与资源接到 Agent 上，本地服务和远端服务的执行位置又不同。盘点时需要找到实际加载的内容、维护者、版本、启动方式、凭据来源，以及它们继续调用的下游服务。

这些内容值得查，是因为扩展会影响操作选择，也可能引入新的执行能力。一个报表 Skill 若带着上传脚本，就要核对上传对象和执行权限；一个查询 MCP 若使用数据库高权限账号，就要检查服务端是否把查询限制在当前员工和任务的范围内。扩展未经审查不等于已经是恶意软件，但它取得的权限不会因为被称为“插件”而变小。

![MCP 交互阶段与潜在风险位置示意](/assets/images/ai-agent-governance/粘贴图-142252.png)

图中列出可用于检查的风险位置；某个位置是否存在可利用问题，还取决于客户端、服务端实现和部署权限。


延伸阅读：[慢雾 MCP 安全检查清单](https://github.com/slowmist/MCP-Security-Checklist/blob/main/README_CN.md)。

还要区分员工拥有的权限和这次工作需要的权限。销售可能有权查看整片区域的客户，某次周报却只需要汇总数字；Agent 沿用同一套凭据时，实际能读到多少，取决于数据源和工具的约束。聊天里写“只看汇总”表达了意图，服务端权限和查询接口才决定它能否取走原始明细。盘点应把这个差距记下来，后面才有依据安排收权或改造工具。

另外，设备和协作方式也在这条路径上。个人电脑能否提供必要的执行限制，外包人员的授权何时到期，共享订阅下能否分清操作者，后台任务在员工离职后是否还会运行，都会影响企业能否落实和撤销权限。敏感任务如果在个人设备上难以受管，可以安排员工在公司远端工作区进行工作，比如一些成熟远程桌面产品，或只参与受控业务入口的工作；针对外包和长期任务，一定要明确负责人、范围及期限。

调查时，用员工说明与技术记录交叉核对即可，不必先收齐所有聊天正文。企业账号事件、受管终端的应用与进程信息、工作区配置，以及批准范围内的网络元数据，都可以帮助还原路径。域名只能说明连接线索，不能说明传了什么；配置中的密钥只记录引用或脱敏标识。发现缺口就标记待核实，私人文件和私人聊天不应成为这份工作台账的收集对象。

盘点完成后，安全团队应能具体描述一项任务：“某员工在受管电脑上，经已确认的模型通道处理客户周报；报表 Skill 的版本已知，MCP 使用部门服务账号，结果写入内部项目空间。目前还不能确认查询是否限制了客户范围。”这样的记录既保留了已经查明的事实，也指出下一步要解决的问题。接下来才能讨论：这项任务本来应该拿到多少数据，又应该允许做到哪一步。

## 盘清用法以后，怎样确定管控要求
{: #ch02}

盘点完软件安装清单、任务流程清单以后，我们应该已经知道员工用了哪些账号、请求经过哪些服务、接入了什么工具。但这份台账还需要转成可以执行的要求：哪些任务可以直接开展，哪些数据需要限制，哪些操作必须审批。

部门和岗位权限可以继续作为基础范围，再按具体任务收紧。同一个研发人员整理公开资料和排查生产故障，接触的数据与操作后果不同；销售起草材料和直接发送报价，也需要不同授权。岗位决定员工原本能做什么，任务决定这一次允许 Agent 代做其中哪一部分。

可以先拿一个完整任务来拆。比如整理客户周报：读取项目文档，查询销售数据，生成报告，再发给项目组。这是分析用的假设场景。任务走到哪一步，数据就交给哪个组件，权限也在那个位置被使用。

![周报请求的旅程：查数据、送模型、做成稿与发出去，每一步都核对接收方](/assets/images/ai-agent-governance/09-report-journey.png)

先看读取阶段。周报可能只需要销售汇总，而工具能够读取整张客户表；文档检索可能只需要当前项目，却能搜到其他客户的材料。这类问题应在数据源限制，即使员工本人有更大权限，也只给本次任务必要的数据。财务对账、人事汇总和合同检索可以用同样的方法分析，分别限定主体、部门、项目和字段。

再看执行阶段。生成一份本地草稿，通常容易检查和撤回；发送报价、修改订单、执行退款，已经改变外部或业务系统状态；生产配置修改还可能影响服务可用性。对后面这些动作，必须明确允许的对象、操作范围和批准条件，不能把读取权限自然延伸成写入权限。

最后看任务是否持续。一次人工发起的报告，可以在任务结束后回收临时授权。变成每天自动生成、自动发送以后，还要管理负责人、重复范围、有效期和停止方式。员工离职、权限变化或工具被撤销时，后台任务不能继续沿用旧授权。

这样就能把任务要求写实。客户周报允许查询指定视图、读取当前项目、使用批准模型，结果先生成草稿；对外发送另行核对收件人和附件。运维排障默认只读，生产变更通过既有变更流程授权。客服查询只开放当前订单，退款由业务系统校验订单归属、额度与审批。市场素材处理则另外登记转写、图片和转换服务，确认未发布材料是否会被上传。

已有分类标准可以直接沿用。数据敏感性与操作后果分别判断：公开资料也可能被用来生成破坏性命令，只读工具也可能读到生产密钥，不能用一个平均分抵消其中的风险。

### 任务范围由谁确认
{: #ch02-1}

任务级授权不能直接相信模型写出的计划。员工在受管入口选择客户周报模板，入口通过企业登录取得身份，再从项目系统查询他与目标项目的关系。业务负责人预先批准模板的数据视图、可用工具和输出位置；服务端据此创建任务记录，绑定项目、期限、策略版本和运行身份。员工可以申请扩大范围，模型也可以提出建议，但扩大授权要经过独立批准。

实际允许的操作，应同时满足员工当前权限、任务范围和工具本身的权限限制。比如员工负责 A、B 两个项目，这次选择 A 项目周报，查询 B 仍应拒绝。项目 ID 由工具参数传来时，服务端要与任务记录比较；任务 ID 只是查找记录的标识，不能拿到它就自动取得权限。执行端还要验证调用者身份和委托关系。

范围不清的临时任务，可以先用只读、有限工作区生成计划或草稿。需要更广的数据或对外写入时，再由员工确认具体对象，并交给有权批准的人或既有业务流程。这样不必让人逐条批准所有工具调用，也不必让一句含糊的目标获得整套账号权限。

没有统一任务平台的公司，也可以先把这些要求放在一个受控业务入口里：固定项目选择、限定查询接口、只生成内部草稿。先让少数高频任务具备可执行的范围，比给所有聊天临时编一个任务标签更有用。

任务要求确定以后，还得指定由谁执行。下面这张图按职责划分控制位置，各列并非请求必须串行经过的网络设备。

![图 01：企业 Agent 安全控制架构](/assets/images/ai-agent-governance/01-enterprise-architecture.png)

企业身份和设备状态由 IAM、MDM 等系统提供；数据源负责对象和行列权限；模型访问层限制接收方及发送内容；工具和运行环境限制实际操作；审计系统把决策与结果关联起来。公司已有的系统可以继续使用，新增工作主要是让它们识别同一个员工、任务和工具调用。

接下来的几章就按这些位置展开。先处理数据怎么进出，再处理扩展和执行，最后说明怎样验证这些限制是否生效。

## 对话和业务数据，应该在哪里检查
{: #ch03}

所谓对话监控，容易让人首先想到输入框。实际执行周报任务时，员工的输入很短，客户明细却来自数据库返回，内部备注来自文档检索，历史摘要和 Skill 指令也可能被一起送给模型。只检查员工输入，覆盖不到后续加入的内容。

因此，需要沿着数据流安排检查，而不是把所有希望放在最后一次敏感词扫描上。

![图 02：AI 对话的数据交接位置](/assets/images/ai-agent-governance/02-conversation-data-boundaries.png)

**数据进入任务之前，先减少不必要的内容。** 周报需要区域汇总，就让数据库返回聚合结果；查询订单时，由服务端限定客户和订单；检索合同按项目权限返回片段。源头少给的数据，就不会继续进入模型上下文、缓存和重试日志。对身份证号、银行账号和认证材料等字段，也应先判断任务是否需要，能用脱敏值或受控操作替代的，就不交出原值。

**发送给模型时，检查实际接收方。** 第一章登记的企业租户、个人账号、API endpoint 和中转路径，在这里应当用于决策。某类数据允许进入哪些服务，规则需要明确。公司网关能够管理的请求，可把身份、数据分类和上游路由绑定；无法改 endpoint 的客户端，则要靠原生受管策略、终端和数据源控制限定用途。网络设备仅看到域名和连接信息时，不能宣称已经检查正文。

检测内容时，先用已有的可靠分类：数据库列标签、文档指纹、内部标记和已知密钥格式。没有标注的商业敏感内容再交给语义分类器。后者适合辅助判断，不应独自签发业务授权；扫描输入也可能含不可信指令，因此扫描器不带业务凭据，不开放写入和执行工具。

扫描失败的状态要单独处理。附件格式不支持、压缩包未解开、内容太长或超时，都说明检查没有完成，不能记成低风险。对附件设置大小、嵌套和解压限制，对高风险外发进入隔离或人工处理。安全培训材料中出现攻击术语，也需要结合任务解释，不能只凭关键词认定恶意。

流式接口还关系到拦截时机。片段如果已经转发出去，后面才拼出敏感串，告警也收不回先前发送的数据。要求泄露前阻断的任务，应先缓冲完整对象检查，或者采用适用范围明确的分块策略。工具参数也要等 JSON 聚合、解析和校验完成，再进入执行环节。

**结果外发时，检查具体业务对象。** 同一服务域名下，公司仓库与个人公开仓库、内部群与外部协作群，授权范围完全不同。发送工具需要检查实际收件人及 BCC、附件标签、目标租户、共享权限和资源 ID。仅允许一个常见域名，仍可能留下外发通道。[S16]

工具内部的外发也在范围内。录音转写、OCR、翻译和图片处理可能上传原文件；员工看到的虽然只是一次转换，数据已经交给另一家服务。准入时登记这些下游接收方，明确临时文件清理和分享方式，不能只登记最外层模型厂商。

这里还要区分检测和留存。检查需要访问正文，不等于应该长期保存所有正文。默认审计可记录身份、任务、来源对象、接收方、分类、决策和结果；风险命中后保留脱敏片段；确需原文调查的流程，再使用单独加密和按案件授权的存储。原始 API body 可能反复包含历史上下文，全量留存会增加成本和敏感数据副本。

关联秘密时可用受控组件生成的 HMAC 标识，并管理密钥版本和访问权限。邮箱、证件号等低熵数据直接做 SHA-256，仍可能被枚举；HMAC 也不等于匿名化。监控目的、范围和留存应向员工说明，具体法律要求由公司结合适用法域评估。上下文来源若无法取得就标记不可用，不能从最终回答反向编造读取记录。

到这里，我们限定了任务能拿哪些数据、能交给谁。但 Agent 会怎样处理这些数据，还受到 Skill 和工具配置的影响，下面继续看这部分。

## Skill 要从安装一直管到更新和撤销
{: #ch04}

员工安装 Skill，是为了复用一套处理任务的方法。这套方法可能只是 Markdown 指令，也可能包含脚本、二进制、依赖和远端引用。企业审查时，要先把实际加载和执行的内容找全。

Agent Skills 规范允许脚本、参考资料和资源文件，`allowed-tools` 则是支持情况因客户端而异的实验性元数据。[S06] 因而只看入口文件或权限声明还不够。需要沿引用关系检查脚本、安装命令、依赖和远端下载，名称、描述与触发条件也一起审核，因为它们会影响模型选择。

审查分两步做。静态分析识别凭据访问、外联、子进程、持久化和安装行为；隔离测试用合成数据与无效凭据观察实际文件、网络和进程行为。这里要分别记录访问尝试和访问成功。对无法解析的文件和未完成的扫描保留未知状态，不给出通过结论。

审完以后，批准需要落到具体制品。假设上周批准的周报 Skill 只写本地文件，本周同名目录里加了上传脚本，旧批准不应该继续有效。批准记录应绑定内容摘要、依赖、策略版本、扫描器版本和有效期，客户端加载时核对实际对象。开发中的版本可以留在隔离通道，正式任务只加载批准制品。

![图 03：Skill 的审查、加载和撤销](/assets/images/ai-agent-governance/03-skill-admission-lifecycle.png)

内部发布可以复用 Git、保护分支、CODEOWNERS 和流水线。发布目录对 Agent 只读，采用不可变制品或原子切换，减少检查后被替换的机会。附录的能力清单用于记录允许访问的文件、服务和工具，但各字段必须有对应执行规则。例如 `subprocess: false` 需要运行环境真的禁止创建进程，写进 YAML 本身没有约束力。

完整性检查还要包含目录结构。稳定序列化记录相对路径、文件类型、执行位、内容摘要和必要链接目标；解包时处理路径穿越、链接逃逸、文件数、总大小和嵌套。平台对大小写、Unicode 和链接的处理不同，也需要在加载端核对。一个目录哈希只能帮助发现变化，不能代替加载前的实际校验。

代码、规则、依赖锁定、版本和有效期应纳入可信发布元数据。信任根通过独立受管渠道交付，防止下载脚本和校验材料被一起替换。签名证明来源与完整性，还要检查版本是否过旧、元数据是否过期。可以参考 SLSA 的构建来源验证和 TUF 的更新机制。[S17][S18]

最后是撤销。确认某个制品有风险后，禁止新加载，并查清已加载它的设备和任务，按影响暂停执行、回收凭据。若代码留下计划任务或修改长期记忆，只删除 Skill 目录并不能结束处置。相应地，共享规则和全局记忆也应记录来源、范围、版本和变更人，外部内容不能自动取得组织策略的信任。

Skill 解决的是加载什么内容、运行哪个版本。MCP 则进一步涉及这些工具以什么身份访问业务系统，需要单独核对。

## MCP 准入之后，权限仍要落实到业务系统
{: #ch05}

管理 MCP 可以按服务来源、执行位置和业务权限依次检查。先确认服务是谁维护的、使用什么凭据、会访问哪些下游，再确定限制应该放在哪里。这里的协议讨论依据 MCP 2025-11-25 版。[S07]

![图 04：本地和远端 MCP 的控制位置](/assets/images/ai-agent-governance/04-mcp-two-control-paths.png)

本地 stdio MCP 是客户端启动的程序，通过 stdin/stdout 交换消息。它能否读取主目录、继承云密钥、创建子进程和访问外网，取决于启动与运行环境。因此要固定程序和依赖来源，按白名单传递环境变量，并限制文件挂载和网络。用 `npx -y package@latest` 启动会让实际代码随时间变化；固定顶层版本以后，也仍要检查依赖、安装脚本和运行时下载。

远端 HTTP MCP 则由服务端执行实际业务调用。假设员工只允许访问某个客户，MCP 却使用数据库管理员账号执行任意查询，员工原来的限制就被服务账号扩大了。客户端记录员工邮箱，不能弥补服务端授权缺失。

解决这个问题，需要把经过认证的员工身份和本次任务范围传到业务授权位置。周报可使用 `sales.monthly_aggregate` 这样的限定工具，由服务端约束客户、项目、行列范围、返回大小和查询时间。跨部门检索保持原文 ACL，共享索引和缓存不能抹掉权限；文档撤销共享以后，后续检索也要更新授权判断。

工具的名字和注解不能替代这一步。任意 SQL 可能调用有副作用的函数，`query` 不保证只读；`readOnlyHint`、`destructiveHint` 由提供方声明，可辅助展示，实际权限仍由企业验证和配置。JSON Schema 校验参数结构，也不能证明用户有权操作目标对象。[S10]

认证时还要区分两段令牌。客户端给 MCP 的 token 应面向该服务，服务核验发行者、目标、有效期和 scope；访问下游使用面向下游的独立令牌，不能透传收到的客户端 token。[S07][S08] JWT 按签名和 claim 契约验证，不透明令牌按授权服务器的机制验证。业务允许的范围与任务允许的范围共同限制调用，避免后台服务身份自动继承全组织权限。

如果采用凭据代理，Agent 可以请求限定操作，由代理使用受限凭据执行，模型只取得结果。确需把 token 交给进程时，限制 audience、scope、资源、时效和网络，同时保证它不会进入日志。共享服务账号无法避免时，代理必须不可绕过，服务端审计记录可信的员工与任务身份。

### 服务更新以后，还要重新核对什么
{: #ch05-1}

MCP 不仅会更新代码，也会更新工具描述和 schema。模型根据描述选工具，描述变化就可能影响行为。因此批准快照包含 endpoint、启动参数、完整工具描述、输入输出 schema 和关键注解。重连或工具列表变化时重新比较，新能力不自动继承旧批准；无法固定版本的 SaaS 服务要有变化告警与临时降权办法。

接入层也要覆盖协商的协议能力。除了 `tools/call`，还可能有 resources、prompts、sampling、elicitation 等交互。未批准的方法不默认透明转发，未知版本和解析失败记录明确状态。不同用户的连接、缓存和断线续传按租户与授权范围隔离，会话 ID 不能作为身份凭据。[S08][S09]

URL 检查覆盖工具参数、OAuth discovery、元数据地址和重定向。公网发现流程限制协议、端口和目标网段，拒绝回环、链路本地及云元数据地址；所需内网服务单独批准。实际建立连接时仍要检查目的地，避免 DNS 解析与使用不一致，IPv6、映射地址和重定向也纳入测试。域名采用规范 hostname 的精确或带点边界匹配，本地 HTTP 服务同时检查 Origin、监听地址与认证。[S08][S09][S19]

这些控制只有在调用必经的位置才有强制效果。如果员工可以拿同一份凭据直连原服务，可选网关就不是完整边界。服务端的对象授权、接入身份和运行环境网络限制需要配合。接下来讨论的执行环境，正是用来限制协议之外的脚本、浏览器和后台行为。

## 工具可以执行到什么程度
{: #ch06}

对研发任务，安装依赖、编译和测试都是正常工作。逐条猜测 Shell 命令是否危险，很难覆盖解释器、脚本和构建系统的间接行为。执行控制应先明确工作区能接触什么，再用 Hook 等机制检查具体调用。

隔离工作区只挂载任务必要输入，输入尽量只读，输出目录单独可写。主目录、SSH agent、云配置、浏览器资料和宿主 Docker socket 默认留在外面；进程使用非特权身份，设置 CPU、内存、进程数、磁盘及网络限制。这样即使模型选择了不合适的操作，能够访问的资源仍然有限。

容器能提供多强的限制，要看权限、挂载和具体实现。挂入整个 HOME 或宿主控制接口会削弱隔离；不可信二进制、多租户和高敏任务可以进一步使用 VM、微虚机或独立远端工作区。文件 API 则需要保证最终访问对象处于授权范围，不能只在检查时做 `realpath`，执行时任由链接变化，形成检查与使用之间的时间差。

依赖准备和业务执行可以分开。准备阶段下载和安装，形成固定镜像；任务阶段挂载业务数据并收紧网络。两阶段若共享不受控的可写缓存，恶意内容仍可能传入后续执行，所以缓存来源、挂载和交接制品都要检查。云端任务也按这个方法逐段验证，不能只看任务主体运行时的网络策略。

浏览器 Agent 有另一套现成权限：登录 Cookie、剪贴板、上传和下载能力。它可以不经过 MCP 就导出客户数据或修改分享。为任务提供独立 profile 或远端浏览器，只登录必要账号，限制上传、下载和剪贴板范围。截图作为证据时也尽量少留，因为它可能带有个人信息和凭据。

### 从准备结果到提交结果
{: #ch06-1}

生成草稿和最终发送应有明确分界。比如员工批准把周报发给内部项目组，执行前收件人变成外部地址，旧批准就不能继续使用。批准信息由实际参数生成，并绑定员工、任务、工具、目标对象、规范化参数摘要、策略版本、有效期和单次 nonce，执行前重新核验。

![审批分镜：员工批准发给内部项目组，执行前收件人改变，旧批准失效](/assets/images/ai-agent-governance/10-approval-storyboard.png)

同样的做法可以用于客服退款的订单与额度、销售报价的客户与版本、运维变更的环境与工单。生产发布绑定提交或镜像摘要，可变对象通过 ETag/version 条件写入，避免审批时看到的对象和执行时不同。业务系统保留最终授权，不依靠模型自己概括“已经获得批准”。

写操作还要考虑重复执行。邮件服务已经接受请求，客户端却超时，再调一次可能重复发送。业务操作使用幂等键，并提供 operation ID 查询；工具报错时先确定下游状态，再决定是否重试。取消请求或断开流不保证回滚，无法确认时记录未知结果。

任务延伸到子 Agent、后台进程或定时运行后，约束也要跟过去。子任务保留父任务关系、数据标签、允许动作、资源和期限，不自动扩大授权；父进程退出后，子进程的文件与网络限制仍然生效。进程关联使用设备、启动时间和稳定实体 ID，避免只依赖会复用的 PID。

![图 07：多个能力组合后的风险](/assets/images/ai-agent-governance/07-composite-risk-control-points.png)

图中是一条假设的组合风险路径。一个任务能读客户数据，另一个任务能发邮件，交接后仍可能组成外发能力。摘要和翻译又会改变数据形式，普通 DLP 无法追踪任意语义变化。因此高敏任务继续依靠源头最小化、任务隔离和出口限制，数据标签作为补充。

长期任务使用明确的工作负载身份，登记业务所有者、频率、预算、到期时间和停止方式，每次运行重新检查权限与制品状态。人员离职或授权撤销后，不仅拒绝新任务，还要核对在途操作、子任务和残留凭据。执行权限到这里有了边界，监控则负责证明它实际如何工作。

## 审计怎样支持检测、调查和停止操作
{: #ch07}

审计设计可以从一个具体问题倒推：如果有人怀疑 Agent 把客户资料发错了，安全团队要怎样查清？首先需要知道谁发起任务、读了哪个对象，再找到发送调用、批准记录和下游结果。只看聊天记录，往往缺少最后的业务证据。

![图 05：审计事件如何对应真实操作](/assets/images/ai-agent-governance/05-audit-evidence-chain.png)

先关联身份。员工、执行 Agent 和下游服务账号分别记录，用可信企业身份、设备或工作负载、任务 ID、调用 ID 将它们对应起来。邮箱和 IP 是辅助属性。关联 ID 由可信组件生成或验证，不接受模型自行填写的身份声明作为授权依据。

再区分决策和结果。`deny` 表示策略拒绝，`not_executed` 表示有证据确认没有执行；`allow` 只表示放行，还要查是否完成。一个调用多次重试时，保留意图 ID、每次 attempt ID 与下游幂等键。附录的 JSON 示例将这些字段分开，拿不到结果时使用 `unknown`，避免把风险评级当成已阻断次数。

采集可靠性决定这条关联能否建立。断网时事件进入持久队列，收到服务端确认才清理本地副本，重复投递按 event ID 去重。采集源和重启代际共同维护序号，监控丢弃数、队列大小、最老未发送时间、时钟偏差和解析错误。文件适配器要处理轮转、截断、半行与重复导入，否则解析失效可能被误认为没有使用活动。

收到的日志可以进入中央追加存储，配合独立摘要锚定和访问审计。但这不能证明终端从未漏记。若哈希链和密钥都能被本地用户修改，整条链可以重建，仍需隔离采集、可信设备身份和业务日志交叉验证。OTel 用于统一传输与 trace，GenAI 字段约定固定版本使用，它本身不提供防篡改保证。[S15]

### 先检测变化，再判断有没有造成后果
{: #ch07-1}

第一类检测针对受管状态变化：新客户端、个人账号切换、未批准 endpoint、Skill 摘要改变、MCP 描述漂移、Hook 或沙箱配置被修改。它们可以触发重新检查和必要降权，但发现新工具不代表员工已经泄露数据。

第二类检测针对任务中的越界动作：未授权数据读取、敏感内容进入不允许的服务、生产写入缺少审批、连续拒绝后换工具尝试等。这些规则需要任务与资源信息，不能仅凭命令词或模型风险分。

第三类是行为关联。某员工短时间内读取客户表、又向外部发送材料，值得调查，但时间上的先后还不能证明发出去的就是那份数据。需要进一步关联产物、内容指纹或数据流证据。附录保留 15 类检测及 SQL 示例，阈值按岗位和任务基线调整，缺少字段的规则先不承诺覆盖。

告警中应展示任务、对象、规则、批准状态、执行结果，以及可以撤销的凭据和任务。分析员据此决定补证、暂停或进入事件响应。把日志交给安全 Agent 分析时，日志内容仍是不可信输入，不能让其中的文字直接触发封号、删除和 Shell 操作。

监控自身也要验证。用合成文件和受控接收端触发一次应拒绝的调用，检查策略、执行端、中央采集和业务结果是否一致。按客户端、工具及运行模式轮换探针，覆盖升级、断网、重启与日志轮转。安装状态和进程心跳可以辅助判断，不能替代这些测试。

最后，故障处理需要提前约定。低风险草稿可在未过期策略、已有权限和有限缓冲范围内继续；生产写入拿不到审批就停在提交前；扫描未完成按未知处理。确认越权或外发后，停止新执行，按风险撤销凭据、切断出口或分享，并行保全证据。请求已发但结果未知时先查业务状态，避免重复操作。能回滚的变更按业务流程恢复，已发送到外部的数据不能承诺完全追回。

## 怎样把安全控制接到不同的 Agent 上
{: #ch08}

前面已经明确了要管什么，接下来才是接入方式的选择。企业可能同时使用 IDE、命令行工具、浏览器助手和云端 Agent，各自暴露的事件与管理能力并不相同。可以先设计一套共同的控制流程，再由适配层连接具体客户端。下面是一种参考设计，用来说明各组件的职责，不代表某个现有插件已经实现了这些能力。

### 先找到能作决定的位置
{: #ch08-1}

以发送客户周报为例，适配层需要在工具执行前取得实际收件人、附件或产物标识，以及可信的员工和任务身份，将它们交给策略服务检查。只有调用尚未执行、客户端又确实会等待并遵守检查结果，这个入口才能承担拦截。若客户端只提供执行后的通知或日志，它能帮助调查，但不能阻止这次发送。

因此，接入时先区分“能够看到”和“能够控制”。会话开始、模型请求、工具执行前后、任务结束都可以作为候选事件，具体能拿到哪些字段、是否支持拒绝、报错和超时后会怎样，要逐个客户端验证。统一事件格式有助于后续分析，却不会凭空补出客户端没有的拦截能力。缺少执行前入口时，高风险操作应通过有授权检查的业务接口或受控执行环境完成。

参考调用流程可以写成下面这样。其中每一步都由程序落实，模型生成的“已审批”文字不能代替审批凭证。

```text
Agent 提出工具调用
  → 适配层解析实际参数，关联可信身份与任务
  → 策略检查数据范围、目标对象、制品状态和审批凭证
  → 拒绝、等待审批，或签发与本次调用绑定的许可
  → 执行端核对许可与当前参数，业务系统再次校验对象权限
  → 记录实际结果，与调用前的决策关联
```

这条流程还需要一个前提：调用不能绕过执行端，改用同一份凭据直接访问业务系统。如果做不到，就必须把关键授权放到服务端，并收紧凭据和网络范围。安全判断只有落在操作必经的位置，才会成为实际约束。

### 适配层记录语义，执行环境限制资源
{: #ch08-2}

客户端通常最容易知道用户正在完成什么任务、模型选择了哪个工具；操作系统和业务服务则更接近真正被访问的资源。这两类能力可以配合。例如，执行前检查发现调用要访问任务外目录，可以立即拒绝；即使检查没有识别出脚本中的间接访问，隔离环境仍应让该目录不可读。

适配器不宜只按工具名称和一段命令字符串判断权限。路径解析、链接、解释器和子进程都可能改变最终访问对象。工具参数应按结构解析，文件与网络限制交给对应执行环境，业务对象的权限留在服务端检查。对没有原生事件的客户端，可以解析日志补充可见性，但要标明采集来源、解析版本和缺失字段，不能把推测出来的操作当成已经确认的业务结果。

### 扩展审查要接到加载动作上
{: #ch08-3}

Skill 和 MCP 的审查可以由独立服务承担，适配层负责报告实际准备加载的制品或工具配置。审查通过后，批准记录绑定内容摘要、依赖、能力范围、策略版本及有效期；加载端再次核对，发生变化就进入重新审查。异步扫描尚未完成时，高风险任务不能提前使用待审能力。

这里最容易出现的断点，是扫描器给出了拒绝结论，客户端却继续加载。验收应直接尝试加载一个未获批准的测试扩展，观察它能否执行，而不只检查控制台有没有红色提示。配置比较也要覆盖实际能力：同名 MCP 可以更换服务地址、工具描述或权限，Skill 可以在名称不变时替换脚本。只比较名称清单，会漏掉这些变化。

### 采集、上传和更新也要有边界
{: #ch08-4}

审计适配层在采集时先去除凭据，再把必要事件送入可靠队列。截短一条记录并不等于脱敏，短 token 仍可能完整留下。身份来自企业认证或受管工作负载，客户端自报的用户名只作辅助信息；中央采集通过确认与去重机制接收事件，离线和丢失状态单独展示。

安全服务自身的数据流也应登记。如果扩展扫描使用远端模型，需要明确哪些内容会被发送、进入哪个租户、按什么规则留存。本地保存审计文件，只说明日志的一个存放位置，不能说明其他检查过程都在本地完成。

最后把适配器、策略和解析规则放进同一套可信发布流程。分别记录版本与兼容关系，用受管渠道分发信任根，校验签名、时效和回退条件。代码可信而策略可被任意替换，仍然会改变最终行为。[S17][S18]

企业接入一个新 Agent 时，可以用同一组问题验收：关键调用是否必经检查，拒绝后是否确实没有副作用，扩展变化能否使旧批准失效，中央审计能否关联到业务结果，撤销是否影响在途和后续任务。通过这些测试，才能明确该客户端可以承接哪些任务，以及哪些能力还需要平台补齐。

## 把客户周报走完一次
{: #ch09}

前面各章分别说明了控制位置。现在把它们放回同一项工作：销售为 A 项目生成本周周报，核对成稿后发给内部项目组。这个案例使用合成数据；配套本地程序实际运行了下面的授权与提交检查，但没有连接真实 Agent、数据库或邮件服务。它用来核对规则之间能否接上，不能代替产品验收。

### 先把业务允许的事情写清楚
{: #ch09-1}

销售通过企业身份进入“项目周报”页面，选择自己负责的 A 项目。业务负责人已经批准这个模板可以读取项目销售汇总和项目内文档，输出限于内部项目空间。任务有效期在本例中设为 30 分钟，实际企业应按工作时长决定；发送必须针对具体成稿另行确认。

| 对象 | 本次任务的约束 | 由谁执行 |
|---|---|---|
| 身份与项目 | 当前员工确实属于 A 项目，任务记录绑定发起人与运行身份 | 企业登录、项目系统、任务服务 |
| 数据 | 只取 A 项目的订单数、金额汇总及获准文档片段 | 数据视图、文档 ACL 与查询服务 |
| 模型与扩展 | 使用批准模型通道和已审查版本，不能临时增加下游服务 | 模型访问层、制品目录、加载端 |
| 成稿 | 写入内部空间，保存不可变版本标识或内容摘要 | 文档服务 |
| 发送 | 批准绑定具体收件人、成稿版本、任务及期限 | 审批入口、执行端、邮件服务 |
| 结束与撤销 | 到期或撤销后拒绝新调用，已提交操作另查状态 | 任务服务及各执行端 |

这里真正减少风险的一步，是查询接口只返回需要的汇总。原始客户明细不进入任务，后面的模型、缓存和扫描器就少了一份需要保护的数据。若任务仍可调用任意 SQL、读取整张客户表，其他表格填得再完整，也没有落实这项要求。

### 正常调用和越界调用分别留下什么
{: #ch09-2}

正常路径中，查询服务返回 A 项目的合成汇总：12 笔订单、总额 36000。Agent 据此生成草稿，员工在受控页面看到收件人和成稿版本，确认后才提交发送。生产实现应从实际待发送对象生成审批内容，不能只展示模型对操作的概括。

本地验证把发送目标替换成内存中的测试收件箱，成稿用固定版本标识表示。每次变更只改变一个条件，并检查业务副作用：

| 验证条件 | 本地运行结果 | 核对的证据 |
|---|---|---|
| 员工为不属于自己的 B 项目申请任务 | 拒绝创建 | 未签发该项目任务 |
| A 项目任务请求查询 B 项目 | 拒绝查询 | 未返回 B 项目数据 |
| 审批后把内部收件人改为外部地址 | 拒绝提交 | 测试收件箱新增 0 条 |
| 审批后把成稿 v1 换成 v2 | 拒绝提交 | 测试收件箱新增 0 条 |
| 项目、收件人和版本都符合批准 | 提交成功 | 收件箱新增 1 条，产生回执 |
| 使用同一操作 ID 重试相同提交 | 返回原回执 | 收件箱仍只有 1 条 |
| 换一个操作 ID 重用已消费审批 | 拒绝提交 | 收件箱没有新增记录 |
| 撤销任务后再次查询 | 拒绝查询 | 服务端重新检查任务状态 |
| 推进测试时钟至任务过期后查询 | 拒绝查询 | 过期状态没有沿用旧授权 |

9 项检查通过，最终测试收件箱只有正常提交产生的 1 条记录。参考程序中的任务与审批由服务端对象保存，没有把模型传入的身份或“已批准”文字当作授权。这个结果证明的是串行参考逻辑符合上述条件。

真实邮件服务需要再验证事务、并发和崩溃恢复：审批消费、操作记录与业务提交如何协调，服务已接收而本地尚未记账时怎样恢复，两个并发重试会不会都成功。本地内存模型没有验证这些问题，也没有验证身份令牌、网络旁路、模型行为、文件隔离、正文 DLP 或跨系统审计可靠性。上线时必须用对应系统的测试补齐。

### 告警怎样变成可以调查的记录
{: #ch09-3}

以“审批后改收件人”为例，实际部署应能关联任务记录、批准的收件人和成稿版本、收到的调用参数、拒绝原因，以及执行端是否发起了下游请求。这里可以记录 `approval_mismatch`；但要声称 `not_executed`，还需要执行端证据。本地验证可以直接检查收件箱，真实系统则应结合操作 ID、出站记录和服务回执核对。

如果邮件已经被服务接受，随后撤销任务，只能阻止后续操作，不能把已经提交的那封邮件记成“已阻断”。若业务结果暂时查不到，就保留未知状态并继续核对。这样的记录才足以指导调查：是批准被改用了、请求重复了，还是控制本身没有经过。

## 企业实施时，先完成哪些工作
{: #ch10}

有了前面的分工，实施可以围绕任务逐步开展。选一个高频、影响可控的任务，再选一个涉及敏感读取或业务写入的任务。例如研发测试修复与客服订单处理，既能验证日常效率，也能检查权限限制。用第一章的台账确认账号、模型路径、Skill/MCP、设备与数据源，再按第二章写清允许范围。

对于未批准的个人账号和中转，需要同时准备可用替代。缺少能力、额度不足或申请过慢，应当分别解决；确需例外的，限定任务、数据和有效期。控制没有准备好的高风险动作继续保留为草稿或只读，不能为了完成推广进度直接放开。

![图 06：三种部署深度和实施顺序](/assets/images/ai-agent-governance/06-deployment-options-roadmap.png)

### 先看现有条件能支撑什么
{: #ch10-1}

不必为了使用 Agent 先建完整安全平台。投入多少，要看数据在哪里、业务操作通过什么接口完成，以及企业有没有能力维护新增组件。同一家公司也可以给公开资料整理和生产运维选择不同方案。

| 企业现有条件 | 可以先做的工作 | 暂不开放的能力 | 何时值得继续投入 |
|---|---|---|---|
| 只有企业 SaaS 账号，缺少开发人员 | 验收租户策略、明确可处理资料、限制分享；用合规材料生成草稿，由人在业务系统提交 | 无法限制目标与权限的自动外发、生产写入；不明通道处理非公开数据 | 高频任务反复需要跨系统复制，人工核对成本明显增加 |
| 有 MDM/EDR 和统一身份，业务接口改造有限 | 受管设备与工作区、批准扩展目录、账号回收、现有日志采集；敏感任务使用远端环境 | 可以绕过检查直连业务的高权限工具；把终端可见性当作正文全覆盖 | 已明确哪些任务需要细粒度数据访问，业务方愿意提供接口 |
| 有接口开发与业务授权能力 | 为周报、订单等任务提供限定接口，绑定身份和项目，管理审批与幂等，关联业务回执 | 服务账号无限放权、只有客户端声明身份的调用 | 多个团队重复建设相同能力，需要统一接入与策略管理 |
| 已有平台团队和高敏自动化需求 | 凭据代理、隔离执行、可信制品发布、统一审计、撤销和故障演练 | 未通过故障及旁路测试的无人值守高后果操作 | 用实际任务量、维护负担和风险后果评估扩展范围 |

表中的暂不开放，针对缺少必要控制的具体动作。只读任务仍可继续，写操作也可以先生成草稿，再由员工通过原业务系统完成。如果一个客户端没有执行前入口，又没有其他必经授权位置，就不能承诺自动发送前拦截；购买更多日志存储也补不上这个缺口。

选择供应商时，可以要求对方用同一组测试演示能力，并交付客户端版本、有效策略、输入、决策和业务结果。采购得到的是哪些已验证的覆盖，应与企业还要承担哪些改造一起写进评估。仅有配置界面或告警截图，不足以确认控制生效。

### 把投入与责任放到任务上
{: #ch10-2}

周报的首期投入可以只包括项目身份核对、限定查询、内部草稿和基本审计；自动发送留到参数绑定、业务授权和重试语义验证以后。预算应分别估算接入开发、日志与模型调用、审批人工、版本维护和故障值守，不能只比较账号或插件单价。

例外也要有人承担：业务负责人说明为什么需要这项能力及可接受后果，数据负责人确认允许范围，IT 或平台团队确认控制条件，安全团队记录缺口、补偿措施、到期日和复核条件。风险接受不能替代必要的法律或合同义务；对没有合适补偿措施的高后果动作，继续保留人工提交。

具体排期可以分三段。第一段完成使用发现、账号和路径分类，限制非公开数据流向不明的通道，并验证一个最小阻断场景。第二段接入高频 Skill/MCP，补制品审查、数据授权、审批绑定和可靠日志。第三段演练变更、断网、重试、撤销与后台任务停止，确认每条关键告警有负责人与恢复办法。时间长短按基础条件调整，不把 30/60/90 天当作必须放开能力的日期。

产品能力优先复用，但要按实际版本验收。Kiro 的 Hook、Claude Code 的受管配置和遥测、Codex 的 requirements 与默认配置，提供的入口和强制程度不同。企业审计 API 的事件范围以接口契约和实测为准。[S03][S11][S12][S13][S14] GitHub Copilot 云 Agent 防火墙的官方说明存在 MCP 和 setup 进程覆盖例外，各条出口仍需单独核对。[S20] 附录保留产品核对表，作为部署检查入口。

团队责任沿现有系统划分：IT 管客户端和设备，IAM 管身份及回收，数据团队管受控视图，研发效能管制品和执行区，SOC 管检测响应，业务负责人确认任务范围和关键动作。几方共同约定任务 ID、身份委托、审批凭证及事件字段，避免各自记录却关联不起来。

效果同样从任务看。研发任务能否完成测试和评审，客服是否正确处理且没有重复变更，财务结果能否追溯到原始单据；安全侧同时统计有效覆盖、关键调用审计完整率、误报、撤销时延和合法任务完成率。阻断增多可能来自更好的检测，也可能来自错误配置，需要复核才能解释。

预算先按采集范围估算。例如假设 500 名活跃员工，每人每日 10 个任务，每任务 30 次工具调用，每调用 3 条事件，每条平均 2KB，原始工具事件约 0.9GB/日。模型事件、全文、索引、副本、备份、扫描费用和人工审核另算。这只是容量计算示例，不是实测产品用量。

试点结束时，同时核对正常任务和越界任务。正常周报是否完成、员工多等了多久，错误收件人是否被拒绝、审计能否解释结果，都应进入评审。再用附录的技术测试和业务场景补充验收，保存客户端版本、有效策略、测试输入、中央事件与业务结果。员工换模型、换账号或增加扩展以后，重新检查受影响的部分。这样企业批准的使用范围、实际执行的限制和持续审计的记录才能保持一致，安全团队也能据此决定下一批任务是否可以开放。

## 工程附录
{: #ch11}

下面保留实施时需要逐项核对的表格和配置示例。正文中的判断可以讨论，验收记录则要写明实际版本、执行位置和证据。

### 数据与动作分级
{: #ch11-1}

D/A 是企业自定义示例，不是行业统一编号。

| 数据等级 | 示例 | 处理要求 |
|---|---|---|
| D0 公开 | 官网、开源代码 | 可进入批准的通用模型 |
| D1 内部 | 一般会议资料、内部流程 | 企业租户；限制公开共享；记录必要元数据 |
| D2 敏感 | 非公开源码、客户资料、财务明细 | 经审批的模型与存储边界；字段最小化；受控工具和出口 |
| D3 严格限制 | 长期密钥、生产认证材料、极敏感业务数据 | 原则上不进入模型上下文；用代理操作、脱敏视图或隔离环境替代 |

| 动作等级 | 示例 | 执行要求 |
|---|---|---|
| A0 解释 | 总结、生成草稿 | 一般无需逐步审批 |
| A1 局部可逆 | 沙箱内改代码、生成本地文件 | 限定目录、可回滚、记录产物 |
| A2 对外或共享写入 | 发消息、创建 PR、更新 CRM | 绑定目标和参数的确认；业务授权；结果审计 |
| A3 高后果 | 生产变更、付款、删库、改权限 | 原则上专用执行通道；独立审批；短期授权；严格故障处理 |

### 故障时的处理约定
{: #ch11-3}

| 故障 | A0/A1 低风险操作 | A2/A3 高风险操作 |
|---|---|---|
| 遥测上传暂时失败 | 持久缓冲，在容量/时效界内继续 | 依策略暂停新外发或写入，不能无限静默继续 |
| 内容扫描不支持格式 | 限制传播，提示待处理状态 | 不能视为扫描通过；隔离或人工检查 |
| 策略服务不可达 | 使用未过期签名策略和既有限权 | 不签发新提升权限；高后果动作拒绝或转人工 |
| 审批服务不可达 | 不需要审批的能力可继续 | 不以超时替代批准 |
| 原生 Hook 报错 | 记录 health failure，限制能力 | 必须验证产品是否阻断；必要时执行层兜底 |
| 本地审计队列满 | 限制任务或停用非必要采集 | 禁止无证据的关键动作，保留控制事件通道 |

### 检测规则起点
{: #ch11-5}

只上线已有数据能支撑的规则。表中的条件需按岗位、项目和任务基线调优，风险评分不等于已确认事件。

| ID | 信号与关联条件 | 依赖数据 | 建议处置与误报处理 |
|---|---|---|---|
| DET-01 | 未批准 Skill/插件被加载，而非仅落盘 | 加载事件、制品摘要、批准目录 | 阻止加载或隔离；开发通道按例外处理 |
| DET-02 | 已批准 Skill 内容或执行位变化，摘要失配 | 文件清单、加载前校验 | 暂停该制品；区分签名发布与本地修改 |
| DET-03 | MCP 工具描述/schema/endpoint 漂移 | 工具集快照、批准版本 | 新能力待审；服务正常升级需变更关联 |
| DET-04 | Agent 访问不在授权集合的密钥/浏览器凭据对象 | 执行层文件事件、任务授权 | 阻断并调查；访问尝试不等于读取成功 |
| DET-05 | D2/D3 数据进入未批准模型或租户 | 上下文标签、模型路由、数据策略 | 发送前拒绝；核对标签来源与误分类 |
| DET-06 | 敏感数据读取后，同任务向未批准目标写入 | 数据读取、工具调用、出口/业务结果 | 高风险关联；仅时间关联时记疑似 |
| DET-07 | 只读办公任务创建进程或执行安装器 | 任务能力、进程遥测、命令类别 | 超出能力立即拒绝；区别批准转换工具 |
| DET-08 | 修改 Hook、策略、遥测 endpoint、沙箱或默认 Agent | 配置变化、主体、有效配置 | 高优先级；排除受管发布流程 |
| DET-09 | 已使用 Agent，但保护探针失效/审计延迟超界 | 独立使用信号、探针、队列健康 | 标记覆盖缺口；高风险任务降级 |
| DET-10 | 同员工/任务访问多租户或越过项目授权 | 可信主体、资源 ID、服务端授权 | 阻断并查凭据/缓存隔离问题 |
| DET-11 | 连续拒绝后换工具完成同类动作 | intent/任务、deny、后续调用和业务日志 | 提高优先级；不要只按工具名称判断 |
| DET-12 | 新建公开分享、外部收件人突增、批量导出 | SaaS 对象审计、参数、历史基线 | 暂停外发；认可审批覆盖的业务活动 |
| DET-13 | 无有效审批执行生产写操作 | 业务操作、审批凭证、资源版本 | 阻止；若已执行进入事件响应 |
| DET-14 | 成本、工具次数、并发或运行时间超任务预算 | 模型计量、工具事件、任务预算 | 限流/暂停；防止重复重试造成业务副作用 |
| DET-15 | 无主后台任务、离职身份任务仍活动 | IAM 状态、调度目录、执行日志 | 停止新执行、回收凭据；核查所有权迁移 |

### 敏感读取与外部写入的关联 SQL
{: #ch11-6}

示例使用企业规范化事件表，需适配 SIEM 字段、去重和时间水位。它提示十分钟内的相关行为，不能单独证明同一份数据已被外发；跨子任务、窗口外及摘要变换还需其他证据。

```sql
SELECT
  r.tenant_id,
  r.employee_id,
  r.task_id,
  r.event_id AS read_event_id,
  w.event_id AS write_event_id,
  w.target_service,
  w.business_status
FROM agent_events AS r
JOIN agent_events AS w
  ON r.tenant_id = w.tenant_id
 AND r.employee_id = w.employee_id
 AND r.execution_context_id = w.execution_context_id
 AND r.task_id = w.task_id
WHERE r.event_type = 'data.read.completed'
  AND r.data_classification IN ('D2', 'D3')
  AND w.event_type = 'external.write.attempted'
  AND w.target_approved = FALSE
  AND w.occurred_at >= r.occurred_at
  AND w.occurred_at < r.occurred_at + INTERVAL '10 minutes';
```

### 上线验收
{: #ch11-7}

记录客户端和 OS 版本、执行位置、有效策略摘要、输入、预期结果、实际结果、中央事件和目标系统证据。用合成数据、无效测试凭据及公司控制的接收端验证。

| 测试 ID | 测试场景 | 通过标准 |
|---|---|---|
| T01 | 用户尝试覆盖受管策略或更换 Agent | 高风险边界仍生效；差异进入审计 |
| T02 | 批准 Skill 的脚本变化，名称不变 | 原批准失效，加载被拒绝或进入隔离通道 |
| T03 | 仅 MCP 描述/schema 改变 | 发现漂移，新能力未自动继承批准 |
| T04 | MCP endpoint 或启动依赖变化 | 身份/摘要不匹配时拒绝，不只比较显示名 |
| T05 | 敏感测试文件通过相对路径、链接与子进程访问 | 执行层仍限制实际文件对象；至少清楚标注不支持的路径 |
| T06 | 工具结果含合成凭据并请求外部发送 | 发送前阻断；日志无凭据原值 |
| T07 | 流式分片跨边界包含敏感标记 | 最终对象检查有效；不先泄露再报阻断 |
| T08 | MCP 输入含未授权租户/资源 | 服务端拒绝，即使客户端绕过提示也不能访问 |
| T09 | OAuth 目标与 token audience 不匹配 | 验证失败，不调用下游资源 |
| T10 | 公网 MCP discovery/重定向指向禁止地址 | 出口控制拒绝；不发生预期外内网访问 |
| T11 | 审批后更换收件人、参数或制品 | 旧审批不可复用；记录明确拒绝原因 |
| T12 | 已执行写操作后模拟超时重试 | 幂等/状态查询有效，副作用不重复 |
| T13 | Hook 崩溃、策略离线或扫描超时 | 与风险等级一致的降级生效；出现 health 事件 |
| T14 | 日志轮转、断网、队列满与重启 | 可重传去重，缺口可见，高风险无证据执行受限制 |
| T15 | 父 Agent 退出，子进程或定时任务继续 | 约束继承；任务到期与撤销能停止后续行为 |
| T16 | 撤销员工/MCP/制品授权 | 新任务与新调用在约定时限内拒绝；在途状态有记录 |
| T17 | 浏览器发送附件或创建公开链接 | 独立会话、对象级策略和必要确认生效 |
| T18 | 公共允许域名中的个人仓库/外部 Bucket | 目标对象识别有效，不因域名白名单放行 |
| T19 | 文档包含正常安全术语与攻击讨论 | 不能仅因关键词阻断；有可解释调优结果 |
| T20 | 无法解析或超出大小的 Skill/附件 | 返回 unknown/unsupported，不被误记为扫描通过 |
| T21 | 两个用户重用连接、缓存或续传 | 数据与结果不会跨用户/租户泄漏 |
| T22 | 签名正确但版本过旧、元数据过期 | 更新策略按版本/时效拒绝或进入明示例外 |
| T23 | 拒绝某工具后使用其他工具做同类动作 | 执行权限仍受限，关联告警能发现意图延续 |
| T24 | 云任务 setup、本地 MCP、普通工具分别外联 | 每个出口均验证；不能以一个防火墙测试代替全部 |

### 用业务任务补充验收
{: #ch11-8}

这些场景补充前面的技术测试，试点选与本公司工作有关的行即可。输入使用合成数据，收件端和业务对象由公司控制；先记录正常任务应当怎样完成，再验证越界时的行为。

| 业务任务 | 故意改变的条件 | 要看见的控制结果 | 业务成功的证据 |
|---|---|---|---|
| 研发修复与 PR | 请求走未批准中转，或改动触发带权限 CI | 非公开源码发送受限；敏感流水线需独立授权 | 批准环境内测试完成，PR 和 CI 身份可追溯 |
| 销售客户方案 | 混入另一客户文档、内部底价，或更换收件人 | 检索隔离与内容权限生效；旧发送批准失效 | 正确客户的批准版本送达指定对象 |
| 客服订单与退款 | 越权订单、超额度操作、写入后超时重试 | 业务服务拒绝越界；幂等机制防止重复副作用 | 正常订单按既有规则处理，状态可核对 |
| 财务对账 | 查询跨主体数据，任务中请求发起付款 | 数据范围受限；对账权限无法直接取得付款权限 | 差异结果能关联原始单据，金额没有误写 |
| 人事资料整理 | 读取其他部门明细，离职后后台任务再运行 | 字段和部门范围有效；撤销后新调用被拒绝 | 授权范围内汇总完成，没有无主任务 |
| 合同检索与起草 | 引入其他项目条款，审批后替换成稿 | 项目 ACL 与批准版本校验有效 | 草稿来源可查，最终确认按原业务流程完成 |
| 录音、图片和材料处理 | 工具调用未登记下游 API，或生成公开链接 | 上传前按数据等级决策；公开分享受控 | 批准服务完成处理，临时材料按约定清理 |
| 运维与定时报表 | 修改生产目标、凭据到期、撤销父任务 | 目标及期限校验生效；子任务和重试受同一授权限制 | 授权任务正常完成，停止和恢复过程可追溯 |
| 外包和个人设备接入 | 项目到期后复用凭据，或下载到未批准设备 | 服务端拒绝过期访问；数据只进入批准环境 | 项目范围内可协作，操作能对应到独立身份 |

### 指标口径
{: #ch11-9}

| 指标 | 推荐定义 | 常见误用 |
|---|---|---|
| 受管活跃覆盖率 | 受管且通过有效性探针的活跃 Agent 实例 / 独立发现的活跃实例 | 已安装插件台数 / 员工总数 |
| 高风险执行审计完整率 | 可关联决策和业务结果的关键调用 / 已知关键调用 | 日志条数越多越好 |
| 扫描覆盖率 | 完整解析并完成规定检查的制品 / 尝试扫描制品 | unknown 算通过 |
| 阻断有效率 | 经执行/业务证据证实未发生的应阻断动作 / 验收中的应阻断动作 | Hook 返回非零即视为阻断成功 |
| 误报率 | 经复核正常的告警 / 经复核告警 | 未处理告警当真阳性 |
| 撤销时延 | 撤销发布到各执行点实际拒绝新操作的时间分布 | 控制台点击成功时间 |
| 审计延迟 | observed/ingested 与 occurred 的差值，含离线分组 | 只看在线设备均值 |
| 业务可用性 | 合法任务完成率、审批等待、额外延迟 | 只优化安全告警数量 |

配套 [CSV 控制清单](/Users/qianli/qianli_zone/BeYourself/安全架构/AI_Agent安全控制落地清单.csv)可用于分配责任和登记证据。P0 项应在相关高风险能力启用前具备；未评估表示还未验证，不是已经通过。
