# 还没开始问 AI，后台已经在做什么？从 GitSpawn 看编程助手的授权边界

作者：千里 / 东方隐侠安全团队  
整理日期：2026-09-08  
研究方式：公开披露核验、Git 文档阅读、固定版本源码对照。未做漏洞复现；本文不提供攻击载荷。当前为研讨稿，尚未发布。

## 先把新闻说准确

9 月 1 日，Manifold 发布 GitSpawn 跨产品研究。它指出的一类问题发生在编程助手自动获取仓库信息时：后台 Git 调用受到本地仓库配置影响，可能触发额外程序。[1]

这不是模型被恶意提示词说服的故事。危险操作可能发生在模型处理任务之前。本文选取有厂商公告和开源代码可交叉核对的 Goose review 路径，不把不同产品的触发条件混写成一个结论。

时间也要分清：Goose 的 CVE-2026-72718 公告发表于 7 月 24 日，厂商列出的修复版本为 1.44.0；9 月 1 日是 GitSpawn 汇总研究的发布日期，不是该漏洞首次公开日期。[2]

## 道：只读的意图，不等于没有执行副作用

我们容易把“查看文件变化”归为低风险：没有提交代码，没有部署，也没有显式执行项目脚本。

但工具如何完成查看，是另一个问题。Git 的 `core.fsmonitor` 支持配置帮助程序，用于获知工作区文件变化。读取状态或差异的过程，可能涉及这样的辅助执行。[3]

因此，要区分两层信任：一层是相信 Git 能正确工作；另一层是允许待检查项目决定 Git 可以调用哪个程序。前者不能自动推出后者。

这个问题也不专属于 AI。AI 产品增加了自动收集上下文的调用机会，使原本需要主动执行的工具操作，可能成为产品的后台步骤。安全分析必须包含这些步骤。

## 法：先拆交付，再拆调用

本文讨论的 fsmonitor 路径，有一个容易被新闻标题省略的前提：攻击者控制的本地 Git 配置已经到达使用者机器。

Manifold 描述的交付方式包括带有 `.git` 目录的项目压缩包、共享目录等。普通 `git clone`、fetch、pull 不会复制远端仓库的 `.git/config`。所以，“克隆任何 GitHub 项目就会触发该问题”不成立。这个判断仅针对本文的配置传播路径，不代表克隆后的依赖安装或其他项目内容没有风险。[1]

审视企业场景时，我们可以按下面的顺序提问：

> 项目从哪里来 → 谁控制本地配置 → 产品何时调用 Git → 子进程受什么限制 → 用户在何时看到授权提示

对于 Goose，厂商说明的入口是用户运行 `goose review`，并非“用户什么都没做”。公告描述的关键是：review 在准备上下文时先收集 Git 差异，此过程不经过模型工具审批。[2]

因此，合适的研讨问题是：**授权了“审查代码”，是否也意味着允许仓库配置驱动额外执行？产品在哪里限制这件事？**

## 术：从固定版本代码看修复落在哪里

我们阅读了两个官方版本的 review handler，并核对修复版调用的公共子进程模块，没有下载第三方 PoC，也没有执行测试载荷。

| 检查点 | Goose 1.41.0 | Goose 1.44.0 |
| --- | --- | --- |
| review 如何建立 Git 命令 | 局部 `git_command(repo_root)` 直接建立 Git 子进程 | `review_git_command(repo_root)` 使用公共 `goose::subprocess::git_command` |
| 参数处理 | 该局部函数设置 `core.quotePath=off` | 保留路径显示参数；公共入口另设 `core.fsmonitor=false` 与 `safe.bareRepository=explicit` |
| 差异收集 | `touched_files`、`collect_diff` 使用局部入口 | 相应函数使用 review 包装后的公共入口 |
| 证据性质 | 固定版本源码观察 | 固定版本源码观察；实际修复状态另以厂商公告佐证 |

1.41.0 的 `handle_review` 先调用 `touched_files` 和 `collect_diff`，再处理后续审查流程。这与厂商对上下文准备阶段的描述一致。[2][4]

修复值得借鉴之处，是把限制落实到建立 Git 子进程的代码入口，而不是要求模型“不要执行危险指令”。`safe.bareRepository=explicit` 是另一个配置限制，不能与禁用 fsmonitor 混为一谈。[5][6]

这份代码对照不能证明所有 Git 调用都走了该入口，更不能证明所有仓库配置、所有 Agent 或沙箱边界已被全面覆盖。源码变化与端到端安全验证是两类证据，我们只报告本次完成的前者。

## 器：一张可以带进企业评审的检查表

| 检查对象 | 应要求提供的材料 | 不足以证明安全的回答 |
| --- | --- | --- |
| 后台初始化 | 启动阶段的工具调用清单、信任检查与子进程创建顺序 | “模型每次执行工具都会询问” |
| 项目接收 | 压缩包、共享目录与正常 clone 的交付规范 | “都来自同事，所以可信” |
| Git 调用封装 | 固定版本的配置限制与调用点覆盖说明 | “只运行了 status 或 diff” |
| 子进程边界 | 运行身份、文件和网络权限、环境变量继承策略 | “产品支持沙箱” |
| 日志和响应 | 能关联到 Agent、Git 及辅助进程的记录与处置责任人 | “聊天记录里没有异常” |

上述是我们建议的评审方法，不是已经完成的企业检查结果。配置限制、运行隔离和监控分别处理不同问题，不能用一个开关替代其他控制。

## 这篇小文章真正要留下的结论

GitSpawn 提醒我们：Agent 的授权范围不能只围绕模型发出的工具调用定义。初始化、上下文收集和底层程序的配置加载，也属于产品的执行过程。

我们能给出的判断是：在所核对的 Goose 路径里，修复落在 Git 子进程创建入口；“看起来只读”的命令名称不能单独作为安全依据。我们尚不能声称任何企业已经暴露，也不能将历史版本结论套到读者当前安装的产品上。

## 需要千里补充的企业判断

下面三项决定这篇文章是否需要突出某个业务场景。只需流程描述，不需要真实项目、凭据、日志或客户名称。

1. 企业或合作方是否经常用完整目录、压缩包、共享盘交付代码？还是主要通过受控 Git 平台克隆？若后者居多，应如实降低本文路径的优先级。
2. 员工的 AI 编程助手由谁安装和更新，能否获得可信的版本清单？这决定我们建议“统一修复”还是先“确认资产范围”。
3. 当前评审是否只看模型权限设置，还是也要求产品说明初始化及子进程行为？这决定文章中最有价值的管理落点。

没有这些信息也可以完成公开技术研讨，但不能替用户所在企业下风险结论。

## SEO / GEO 随研究积累

建议围绕一个主问题组织最终正文：**AI 编程助手还没开始处理任务，为什么已经可能执行项目相关程序？**

保留 GitSpawn、Goose、授权边界等必要术语，并在开头写清日期、版本与证据方式。单列“普通 clone 是否受此路径影响”“这是不是提示注入”“修复位于哪里”三个可直接回答的问题。结论旁边保留前提与来源，避免摘要被引用后丢失限制条件。

正式发布前后用同一组问题人工观察搜索和 AI 引用，记录平台、时间、联网状态和原始回答。此阶段尚未建立基线，不填写收录率、排名或引用增长数字。
