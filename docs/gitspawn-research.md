## 要回答的问题

AI 编程助手在用户授权前自动收集项目上下文时，是否可能触发项目携带的可执行配置？
本文区分两个待验证判断：Git 状态查询能否触发配置指定的程序；特定版本 Agent 是否会在信任确认或沙箱之外执行这类查询。前者成立不等于后者已经得到证明。

## 新闻依据与证据边界

- Manifold 于 2026-09-01 发布 GitSpawn 研究，描述后台 Git 调用与不可信仓库配置组合导致的执行风险。本文所讨论的交付路径需要携带 `.git` 目录，例如项目压缩包或共享目录；普通 clone、fetch、pull 不传播远端 `.git/config`。这是漏洞披露，不能表述为已确认的企业受害事故。产品修复状态必须按实验当天版本再次核实。
- Goose 官方公告确认了 `goose review` 与 `core.fsmonitor` 组合的命令执行问题。正式引用产品版本、修复提交前，应完整核对公告，而不只引用新闻汇总表。
- Git 官方文档说明 `core.fsmonitor` 可指定帮助程序。它是 Git 的功能；研究重点是 Agent 在何时、以什么权限、在什么隔离边界内调用 Git。

## 最小实验

使用独立临时环境，不在官网仓库写入测试 Git 配置，不挂载真实凭据。不提供外联、持久化或数据读取载荷，探针只在测试目录留下标记。

| 对照 | 目的 | 当前结果 |
| --- | --- | --- |
| 干净仓库执行 Git 状态查询 | 验证采集方法不产生假阳性 | 未测试 |
| 测试仓库执行相同状态查询 | 验证帮助程序是否被调用 | 未测试 |
| 对同一查询显式关闭 fsmonitor | 检查该特定路径的控制效果，不代表防住所有 Git 配置路径 | 未测试 |
| 正常 clone 后执行相同查询 | 验证交付前提，不将压缩包路径扩大为普通克隆风险 | 未测试 |
| 一个受影响历史版本与对应修复版本的 Agent | 验证初始化时机及修复效果 | 未测试 |

每次记录 OS、Git 与 Agent 版本、项目来源、启动参数、信任与审批设置、探针时间、相关子进程、退出状态及正常任务能否完成。
必须有进程证据才能判断谁触发执行；有信任提示的时间证据才能判断是否早于授权；仅看到标记文件不足以证明沙箱逃逸。
