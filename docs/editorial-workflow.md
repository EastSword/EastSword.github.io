# 小文章创作与传播流程

适用：千里 / 东方隐侠安全团队。先独立写文章，成熟后再提炼进研究课题。道法术器可以用于内部整理，不作为文章的固定标题或必填结构。

## 草稿交付约定

所有需要千里修改、润色的稿件，必须保存到官网工作台的原生草稿中，包括官网文章、公众号与其他渠道的改编稿。不能以聊天正文、docs 文件或直接写入 `_articles` 作为草稿交付的替代。当前编辑服务为 http://127.0.0.1:8971/；8917 是独立的目录浏览服务。

新稿通过工作台的新建、保存接口进入「原创文章」，标题、摘要、作者、正文等字段与表单一致。渠道稿使用独立路径和带渠道名的标题，作为单独草稿保存，不混进官网原文，也不自动写入官网。交付时提供后台入口和准确的稿件标题，并验证草稿能打开、保存、重新读取和生成预览。

继续修改前先读取后台当前草稿，保留千里已经做的编辑。保存使用服务返回的 version、revision；发生冲突时重新读取并合并，不覆盖新版本。只有决定进入发布流程的官网稿才执行「写入官网」，其他待审稿保持隔离。

## 每篇先决定值得回答什么

选题卡只写五项：谁会遇到这个问题、他正在做什么决定、最近出现了什么证据、我们能补充什么判断、还缺什么材料。

新闻提供入口，具体问题决定文章价值。只有新闻转述、没有额外判断时，先放资讯或资料库；有一处可核对的源码差异、一个被忽略的条件或一条能用于评审的问题，就值得尝试短文。不要为了字数拼成行业综述。

GitSpawn 本期选题卡：

- 读者：引入 AI 编程助手的开发者、安全工程师。
- 决定：模型工具审批之外，还要检查哪些后台行为。
- 证据：9 月 1 日汇总研究、7 月 24 日 Goose 公告、两个固定版本源码。
- 我们补充：把“准备上下文”纳入执行边界，并指出包含 .git 的交付前提。
- 尚缺：真实企业的交付流程、版本和日志材料。没有这些材料，就不写实际受影响或实测有效。

## 写作与编辑

先用一句话写出本文判断，再挑足够支撑它的材料。建议正文约 800–1500 字，证据需要时可以更长；通常三到五分钟读完。自然地从场景走到证据和判断，不强制章节数、表格或问答形式。

我负责检索一手来源、对照证据、起草与压缩；千里负责确认观点是否代表本人、提供可公开的实践观察。没有发生过的经历，不写成“我们在客户现场发现”。需要人工验证的事项单独留在内部记录，不让读者替我们完成论证。

编辑完成的判断标准：标题准确；第一屏能看出问题；核心判断能找到来源；事实、推断和建议分得开；删掉任一段都会损失必要信息。数字、时间、版本、触发前提逐项核对。对于当前这类研讨，只做公开材料和静态分析。

每篇保留一份轻量证据记录：结论、来源 URL、发布日期、适用版本、证据类型、未验证项。修订时沿这份记录回查。

## 官网作为可维护的原文

1. 在 8971「原创文章」编辑，保存后预览。新文章不填写 topic 也可以成立。
2. 检查标题、摘要、作者、实际发布日期、稳定 URL、来源链接和手机排版。发布日期在正式上线时确认；实质修订才更新 updated。
3. 看发布中心的变更清单，核对是否混入无关修改；完成构建，再执行发布。
4. 等部署完成，检查线上文章及文章列表，而不是把本地预览或推送成功当成已上线。
5. 记录官网 URL 和发布版本，之后修正原文，保留必要的更正说明。

当前仓库已有 canonical、摘要元标签和 jekyll-sitemap。尚未在文章模板中发现 Article JSON-LD；robots.txt 文件也不存在，缺少该文件本身不表示禁止抓取。这只是本地模板检查，不代表线上已收录或搜索站长平台已配置。结构化数据可列入后续技术改进，不阻塞首篇发布。

本流程不是自动发布授权。本期仍处于本地编辑状态。

## 分发：先做两处，再决定是否扩展

首月按每两周一篇安排，总投入建议控制在每篇 4–6 小时。官网维护完整原文，先配一篇公众号改编，再从 FreeBuf、CSDN 中选一个最贴近本期读者的渠道。B 站只在画面能解释问题、且有制作余力时做，不要求每篇四平台齐发。

| 渠道 | 这一版服务谁 | 本期改编方式 |
| --- | --- | --- |
| 官网 | 需要核查与长期引用的人 | 保留条件、源码对照、参考来源和修订日期 |
| 公众号 | 日常关注 AI 应用安全的读者 | 从“帮我看看代码”切入，缩短源码术语，保留交付前提和修复版本 |
| FreeBuf | 安全研究与企业防护读者 | 突出后台调用边界及证据范围，按投稿要求准备 |
| CSDN | 开发者 | 突出 Git 配置与调用入口的变化，不扩写成未经验证的教程 |
| B 站 | 更适合听讲解的读者 | 2–3 分钟讲解项目、Git、子进程的关系，明确这是示意而非复现录像 |

各渠道统一署名“千里 / 东方隐侠安全团队”，在允许的位置附原文和来源。外部平台的原创声明、外链和转载规则在提交时核对。不要默认首发一定让官网成为搜索引擎选定的规范页，也不要假设外部平台支持自定义 canonical。

如果只有很少时间，发官网和一个渠道就够。每个平台保留发布 URL、日期、版本，方便同步勘误。投稿、发布由千里操作或另行明确授权。

## SEO 与 GEO 随文章一起做

写作前记录一个主问题和两三个自然变体，正文确实回答即可，不重复堆关键词。本期问题是“AI 代码审查的后台 Git 调用为什么也需要权限限制”；自然变体可以是“GitSpawn 是什么”“普通 clone 会带入 .git/config 吗”“Goose 如何修复 GitSpawn”。

SEO 发布检查：正文可直接读取、文章列表有入口、标题与摘要各自准确、canonical 指向正式 URL、站点地图包含文章、没有误设 noindex。站长平台已验证时再检查收录和查询表现；账号验证或实际数据读取需要千里参与，未知值记录为未取得。

GEO 的内容实践：让关键判断带有明确对象、条件、版本和近旁来源；保持作者身份一致；只在有用时放一张对照表；保留可追溯的更正。目标是让引用不脱离条件，不制造虚假的权威、引用或问答页面。

Google 对 AI Overviews / AI Mode 的官方说明仍以通用 SEO 为基础，不要求专用 AI 文件或特殊结构化数据，也不保证收录。这只说明 Google 的这些功能，不能外推到所有生成式搜索服务。[1] Article 结构化数据可帮助描述文章、作者与日期，且需与页面一致；它不是排名或 AI 引用保证。[2]

同稿多渠道时，官网保留稳定原文地址；外站尽量做面向其读者的改编并注明原文。canonical 是规范化信号，搜索引擎仍可能选其他 URL，不把它当强制指令。[3]

## 发布后如何判断有没有用

发布前留一次基线；发布后第 7 天看抓取与传播问题，第 28 天做一次内容复盘。新站收录较慢时继续观察，不把没有流量直接判断为选题失败。

| 观察 | 记录什么 | 用来决定什么 |
| --- | --- | --- |
| 搜索 | 收录状态、实际查询、展示、点击、统计窗口 | 修复发现问题；标题是否匹配真正的查询 |
| 渠道 | 各平台可取得的阅读、收藏、有效评论和统计口径 | 是否值得继续投入该渠道；不同平台数据不直接相加比较 |
| 生成式搜索 | 固定问题、产品/模型、联网状态、日期、回答截图、是否引用官网 URL、是否准确保留条件 | 发现被误读或未回答的问题，不把单次结果当稳定排名 |
| 专业反馈 | 具体纠错、同行引用、带场景的问题、主动联系 | 优先修正文稿或形成下一篇文章 |

生成式搜索观察使用不提示站名、不粘贴文章 URL 的固定问题。让模型阅读指定网址后复述，不能算自然发现。每轮使用相同问题，记录波动；没有可靠引荐数据时，不宣称 GEO 带来了多少流量。Google 的 AI 功能流量包含在 Search Console 的 Web 数据中，不将其全部算作 GEO 成果。[1]

首月目标是完成两篇有证据的短文、每篇至少一个站外改编和一次复盘，建立自己的基线，不承诺爆款阅读量。

## 什么时候更新研究课题

当文章产出可复用的判断、已有结论需要修正，或数篇文章能回答同一个更大的问题时，再讨论归档。先提炼一句结论、支持证据、适用条件和未解决的问题，再决定是否更新课题的结论、阅读路径和维护记录。只因发了新文章，不自动改课题状态。
